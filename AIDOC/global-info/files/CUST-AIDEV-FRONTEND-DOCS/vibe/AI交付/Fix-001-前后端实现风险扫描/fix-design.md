# Fix 设计文档 — Fix-001 第0批次（业务逻辑）

## 1. 设计目标

围绕第0批次业务逻辑错误，设计最小可交付修复方案，确保：

- 业务流程闭环（支付、公告触达、登录态与门禁）
- 状态一致（前后端对同一业务状态认知一致）
- 回归可控（保留现有可用能力与接口契约）

---

## 2. 修复方案

### 2.1 支付链路（`F-05`、`B-17`、`B-18`、`B-19`）

- 前端移除“直接调用支付回调”行为，仅保留支付发起与结果查询。
- 后端支付回调改为受控入口，补齐回调幂等与并发保护（按支付单/业务单去重）。
- 支付详情接口增加 owner 归属校验，禁止跨用户读取。
- 退款接口增加“可退额度”校验，区分部分退款与全额退款状态语义。

**影响范围**
- H5：`billing/BillDetailView` 与支付 API 封装。
- Backend：`billing` 模块服务层与回调入口校验链路。

### 2.2 公告触达（`B-10`）

- 直接复用 notice-center 既有修复主方案，不在本目录重复实现细节。
- 本批仅做联动约束：支付与前端状态修复时，不得引入公告 H5 可见性回归。

**影响范围**
- Backend `notice` 模块（引用既有 Fix-001）。

### 2.3 前端状态与门禁（`F-01`、`F-08`、`F-09`、`F-10`、`F-12`）

- 统一 401 清理入口，确保 token、store、守卫缓存状态一致重置。
- 初始化检查策略由 fail-open 调整为 fail-close（或明确维护态），避免异常放行。
- H5 增加认证态门禁元数据与守卫处理。
- 请求层统一响应解包契约，消除视图层重复 `res.data` 解包。
- 首页移除业务硬编码，改真实接口或明确空态/占位态。

**影响范围**
- PC/H5 `router/guard`、`store/user`、`utils/request`、`home`/`billing` 页面。

---

## 3. 回归测试策略

### 3.1 核心用例

- 支付成功/失败/重复回调/并发回调。
- 支付详情跨用户访问（应拒绝）。
- 退款超额申请（应拒绝）。
- 401 后登录态重置与页面跳转一致性。
- 初始化检查失败场景路由行为。
- 未认证业主访问受限页面拦截。
- 公告发布与重推后目标用户可见性（联动验证）。

### 3.2 不变行为验证

- 既有登录流程与主导航流程不变。
- 账单状态流转主语义不变。
- 公告审批流与发布状态机不变。

---

## 4. 风险与缓解

- 风险：支付链路改造与现有 Mock 流程冲突。  
  缓解：保留可配置开关，灰度切换并保留审计日志。

- 风险：前端统一解包可能影响历史页面。  
  缓解：先补类型与回归清单，再分页面迁移。

- 风险：门禁收紧导致“原可访问页面”被拦截。  
  缓解：同步产品与测试确认拦截矩阵，补可解释提示。
