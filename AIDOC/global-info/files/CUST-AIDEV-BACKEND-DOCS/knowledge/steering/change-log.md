# 变更日志规范

本规范定义了 SPMP 项目中各域的变更日志记录流程，确保所有变更可追溯。

---

## 一、何时创建变更日志

以下情况**必须**创建变更日志：

| 触发场景 | 说明 |
|---|---|
| 新功能开发完成 | 完成 requirements → design → tasks → implementation 全流程后 |
| API 接口变更 | 新增、修改、删除 API 接口 |
| 数据库结构变更 | 表结构修改、索引调整、存储过程变更 |
| 业务流程调整 | 核心业务逻辑修改 |
| Bug 修复 | 生产环境问题修复 |
| 配置变更 | 系统配置、参数调整 |

---

## 二、目录结构

```
domain/{domain}-center/change-log/
├── README.md                    # 变更日志索引
├── 2025-01/                     # 按月归档
│   ├── CL-2025-001.md
│   └── CL-2025-002.md
├── 2025-02/
│   └── CL-2025-003.md
└── 2025-03/
    └── CL-2025-004.md
```

---

## 三、变更编号规则

格式：`CL-YYYY-NNN`

- `CL`：Change Log 固定前缀
- `YYYY`：年份
- `NNN`：年度序号，从 001 开始

示例：`CL-2025-001`、`CL-2025-002`

---

## 四、变更类型分类

| 类型 | 标识 | 说明 |
|---|:---:|---|
| 新增 | ✨ ADD | 新增功能、接口、表等 |
| 修改 | 📝 MODIFY | 修改现有功能、接口参数等 |
| 删除 | 🗑️ DELETE | 删除功能、接口、字段等 |
| 修复 | 🐛 FIX | Bug 修复 |
| 优化 | ⚡ OPTIMIZE | 性能优化、代码重构 |

---

## 五、变更日志模板

```markdown
# CL-YYYY-NNN - {变更标题}

## 基本信息

| 项目 | 内容 |
|---|---|
| 变更编号 | CL-YYYY-NNN |
| 变更类型 | ✨ ADD / 📝 MODIFY / 🗑️ DELETE / 🐛 FIX / ⚡ OPTIMIZE |
| 变更日期 | YYYY-MM-DD |
| 关联需求 | [需求编号/PRD链接] |
| 影响范围 | [涉及的域/模块] |
| 变更人 | [姓名] |

## 变更内容

### 变更前
[描述变更前的状态，如有]

### 变更后
[描述变更后的状态]

## 影响分析

### API 变更
| 接口路径 | 变更类型 | 说明 |
|---|---|---|
| POST /api/v1/xxx | 新增 | 新增xxx接口 |

### 数据库变更
| 表名 | 变更类型 | 说明 |
|---|---|---|
| table_name | 新增字段 | 新增 xxx 字段 |

### 依赖影响
[说明对其他模块或系统的影响]

## 测试验证

- [ ] 单元测试通过
- [ ] 集成测试通过
- [ ] 接口测试通过

## 备注
[其他需要说明的内容]
```

---

## 六、操作流程

1. **变更完成时**：在对应域的 `change-log/{YYYY-MM}/` 目录下创建变更日志文件
2. **更新索引**：在 `change-log/README.md` 的最近变更表中添加记录
3. **跨月归档**：每月初将上月变更移入对应月份目录

## 八、注意事项

1. **强制性**：变更日志是强制性的开发流程，不可跳过
2. **及时性**：变更完成后应立即创建变更日志
3. **完整性**：变更日志应完整记录所有影响
4. **可追溯**：变更日志应保留历史记录，便于后续追溯
