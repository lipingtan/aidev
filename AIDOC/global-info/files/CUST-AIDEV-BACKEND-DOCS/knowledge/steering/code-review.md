# 代码审查规范

本规范定义了 SPMP 项目中各域的代码审查流程，确保代码质量可保障。

---

## 一、何时进行代码审查

以下情况**必须**进行代码审查：

| 触发场景 | 审查类型 |
|---|---|
| 功能开发完成 | 完整审查 |
| Bug 修复 | 针对性审查 |
| 代码重构 | 完整审查 |
| 性能优化 | 性能专项审查 |
| 安全相关变更 | 安全专项审查 |

---

## 二、目录结构

```
domain/{domain}-center/code-review/
├── README.md                    # 代码审查索引
├── 2025-Q1/                     # 按季度归档

│   └── CR-2025-Q1-002.md
├── 2025-Q2/
│   └── CR-2025-Q2-001.md
└── 2025-Q3/
    └── CR-2025-Q3-001.md
```

---

## 三、审查编号规则

格式：`CR-YYYY-QN-NNN`

- `CR`：Code Review 固定前缀
- `YYYY`：年份
- `QN`：季度（Q1/Q2/Q3/Q4）
- `NNN`：季度序号，从 001 开始

示例：`CR-2025-Q1-001`、`CR-2025-Q1-002`

---

## 四、审查维度

| 维度 | 检查项 |
|---|---|
| **代码规范** | 命名规范、代码格式、注释完整性 |
| **安全性** | SQL注入、XSS、敏感信息泄露、权限校验 |
| **性能** | SQL性能、缓存使用、循环优化、内存泄漏 |
| **可维护性** | 代码复杂度、模块耦合度、重复代码 |
| **测试覆盖** | 单元测试覆盖率、边界条件测试、异常处理测试 |

---

## 五、问题级别分类

| 级别 | 标识 | 说明 | 处理要求 |
|---|:---:|---|---|
| 严重 | 🔴 Critical | 安全漏洞、数据丢失风险、系统崩溃 | 必须立即修复 |
| 重要 | 🟠 Major | 功能缺陷、性能问题、逻辑错误 | 必须修复后才能合并 |
| 一般 | 🟡 Minor | 代码规范问题、可读性问题 | 建议修复 |
| 建议 | 🟢 Suggestion | 优化建议、最佳实践 | 可选修复 |

## 七、操作流程

1. **审查时**：在对应域的 `code-review/{YYYY-QN}/` 目录下创建审查报告
2. **更新索引**：在 `code-review/README.md` 的审查记录表中添加记录
3. **问题跟踪**：在审查报告中更新问题状态，直至所有严重和重要问题修复完成
4. **季度归档**：每季度初将上季度审查移入对应季度目录

## 九、注意事项

1. **强制性**：代码审查是强制性的开发流程，不可跳过
2. **时机**：代码合并前应完成代码审查
3. **完整性**：代码审查应覆盖所有审查维度
4. **问题跟踪**：严重和重要问题必须修复并验证后才能合并
