## 测试目标

### 总体目标

本次 CR 的测试目标是验证付款申请模块的核心业务逻辑正确性、接口契约符合性以及系统在并发和边界条件下的稳定性，确保变更上线后不引入回归缺陷，满足业务验收标准。

### 质量标准

| 质量指标 | 目标值 | 说明 |
|----------|--------|------|
| 单元测试覆盖率（行覆盖） | ≥ 80% | 核心业务逻辑（Service 层）覆盖率不低于 80% |
| 单元测试覆盖率（分支覆盖） | ≥ 70% | 关键条件分支（状态流转、权限校验）需全覆盖 |
| 集成测试通过率 | 100% | 所有集成测试用例必须全部通过，不允许跳过 |
| 核心接口响应时间（P95） | ≤ 500ms | 在 100 并发下，核心查询接口 P95 响应时间不超过 500ms |
| 缺陷遗留率（严重/高） | 0 | 严重和高优先级缺陷必须在上线前全部修复 |
| 缺陷遗留率（中） | ≤ 2 条 | 中优先级缺陷可带缺陷上线，但需记录并制定修复计划 |

## 测试范围

### 在范围内

| 功能模块 | 测试内容 | 测试类型 |
|----------|----------|----------|
| 付款申请 CRUD | 创建、查询（列表/详情）、修改、删除申请单 | 单元测试 + 集成测试 |
| 审批流程 | 提交审批、审批通过、审批拒绝、撤回申请 | 单元测试 + 集成测试 |
| 状态机流转 | 所有合法状态流转路径、非法流转的拒绝 | 单元测试 |
| 权限控制 | 不同角色对各接口的访问权限（RBAC） | 集成测试 |
| 数据隔离 | 普通用户只能查看本人数据，管理员可查看全部 | 集成测试 |
| 参数校验 | 必填字段、金额范围、字段长度等输入校验 | 单元测试 + 集成测试 |
| 消息通知 | 审批状态变更时触发通知，通知失败不影响主流程 | 集成测试 |
| 申请编号生成 | 编号格式正确性、并发场景下的唯一性 | 单元测试 + 集成测试 |

### 不在范围内

| 排除项 | 排除原因 |
|--------|----------|
| 前端页面 UI 测试 | 前端由独立团队负责，有独立测试计划 |
| 用户中心服务内部逻辑 | 外部依赖服务，不在本次 CR 变更范围内 |
| 消息通知服务内部逻辑 | 外部依赖服务，仅测试集成点（发送调用是否正确触发） |
| 性能压测 | 本次 CR 为新增功能，性能基线测试在 UAT 阶段单独进行 |
| 安全渗透测试 | 由安全团队在 UAT 阶段独立执行 |
| 数据迁移验证 | 本次 CR 无历史数据迁移需求 |

## 测试金字塔

```
          /\
         /  \
        / E2E\        ← 少量：核心业务流程冒烟测试（手动执行）
       /------\
      /        \
     / 集成测试 \     ← 适量：接口契约、数据库交互、外部服务集成
    /------------\
   /              \
  /   单元测试     \  ← 大量：业务逻辑、状态机、工具类、参数校验
 /------------------\
```

### 单元测试（Unit Tests）

**目标覆盖率**：行覆盖率 ≥ 80%，分支覆盖率 ≥ 70%

**测试重点**：

| 测试层 | 测试类 | 测试内容 |
|--------|--------|----------|
| Service 层 | `PaymentServiceTest` | 创建申请业务逻辑、参数校验、状态流转 |
| Service 层 | `ApprovalServiceTest` | 审批流程逻辑、权限校验、状态变更 |
| 枚举/工具类 | `PayOrderStatusTest` | 状态枚举合法性、状态流转规则 |
| 工具类 | `OrderNoGeneratorTest` | 申请编号格式、边界日期（跨天、跨月） |
| 参数校验 | `PaymentRequestValidationTest` | 必填字段、金额范围、字段长度 |

**框架**：JUnit 5 + Mockito（Mock 外部依赖）

**执行命令**：

```bash
mvn test -pl payment-service -Dtest="*Test" -DexcludedGroups="integration"
```

### 集成测试（Integration Tests）

**目标**：验证各层之间的协作正确性，包括数据库交互和外部服务调用

**测试重点**：

| 测试类 | 测试内容 | 依赖 |
|--------|----------|------|
| `PaymentControllerIT` | 接口请求/响应格式、HTTP 状态码、认证鉴权 | Spring Boot Test + MockMvc |
| `PayOrderMapperIT` | CRUD 操作、分页查询、条件查询 | Testcontainers（MySQL） |
| `PaymentServiceIT` | 完整业务流程（含数据库写入） | Testcontainers（MySQL + Redis） |
| `NotificationServiceIT` | 消息通知触发时机、失败重试 | WireMock（Mock 消息服务） |

**框架**：JUnit 5 + Spring Boot Test + Testcontainers + WireMock

**执行命令**：

```bash
mvn test -pl payment-service -Dgroups="integration"
```

### E2E 测试（端到端测试）

**执行方式**：手动执行，在 SIT 环境完成联调后进行

**覆盖场景**：

1. 完整付款申请提交与审批通过流程
2. 付款申请被拒绝后重新提交流程
3. 申请人撤回申请后重新编辑提交流程
4. 无权限用户访问接口返回 403 场景

## 测试数据管理规范

### 测试数据准备策略

| 策略 | 适用场景 | 说明 |
|------|----------|------|
| `@BeforeEach` 初始化 | 单元测试 | 每个测试方法前重置 Mock 状态，确保测试隔离 |
| `@Sql` 注解 | 集成测试 | 在测试方法执行前通过 SQL 脚本插入测试数据 |
| Testcontainers 初始化脚本 | 集成测试 | 容器启动时执行 `schema.sql` 和 `data.sql` 初始化表结构和基础数据 |
| Builder 模式构造对象 | 单元测试 | 使用 `PayOrderBuilder` 构造测试用实体，避免大量 setter 调用 |

**测试数据文件位置**：

```
src/test/resources/
├── sql/
│   ├── schema.sql          # 测试数据库表结构（与生产 DDL 保持同步）
│   ├── data.sql            # 基础字典数据、角色权限数据
│   └── test-cases/
│       ├── payment-crud.sql    # 付款申请 CRUD 测试数据
│       └── approval-flow.sql   # 审批流程测试数据
└── application-test.yml    # 测试环境配置（覆盖生产配置）
```

### 测试数据清理策略

| 清理方式 | 适用场景 | 说明 |
|----------|----------|------|
| `@Transactional` 回滚 | 集成测试（读写操作） | 测试方法结束后自动回滚事务，不污染数据库 |
| `@AfterEach` 手动清理 | 无法使用事务回滚的场景（如异步操作） | 手动删除测试数据，确保测试后数据库干净 |
| Testcontainers 容器隔离 | 所有集成测试 | 每次测试套件使用独立容器，容器销毁后数据自动清除 |

### 测试数据隔离策略

1. **单元测试**：完全使用 Mock，不访问真实数据库，天然隔离
2. **集成测试**：使用 Testcontainers 启动独立数据库容器，与开发/生产环境完全隔离
3. **测试数据前缀**：集成测试插入的数据使用固定前缀（如 `TEST_`），便于识别和清理
4. **并行测试隔离**：不同测试类使用不同的数据集，避免并行执行时的数据竞争

### 敏感数据处理

- 测试数据中不使用真实的用户信息（姓名、手机号、身份证号等）
- 使用 JavaFaker 生成符合格式的随机测试数据
- 测试配置文件（`application-test.yml`）不提交真实的数据库密码，使用环境变量或测试专用账号
