# 日志分析器 - 通用根因分析

## 概述

本技能为应用日志提供智能根因分析，通过自动检测格式、识别异常、关联事件，并生成带有支持证据的可执行洞察。

**核心能力：**
- 自动格式检测（JSON、文本、常见框架日志）
- 多维度分析（异常、性能、依赖、业务逻辑）
- 时间窗口关联和事件排序
- 有证据支持的根因假设
- 可执行的修复建议

## 使用场景

当你需要以下功能时使用本技能：
- 调查应用故障或错误
- 诊断性能下降
- 理解分布式系统中的级联故障
- 分析生产事故
- 审查QA/测试问题的日志

## 快速开始

### 基本用法

```bash
# 分析日志文件
/log-analyzer /path/to/application.log

# 分析指定时间范围
/log-analyzer /path/to/application.log --since "2025-01-29 10:00" --until "2025-01-29 11:00"

# 分析特定日志级别
/log-analyzer /path/to/application.log --level ERROR

# 聚焦性能问题
/log-analyzer /path/to/application.log --focus performance
```

### 粘贴日志内容

```bash
# 直接粘贴日志内容
/log-analyzer
# 然后在提示时粘贴你的日志内容
```

## 分析维度

### 1. 异常与错误分析

**检测内容：**
- 异常类型和频率
- 错误聚类和模式
- 根因异常vs级联错误
- 堆栈跟踪聚合

**输出：**
- 按频率排序的顶级异常
- 错误传播链
- 根因异常识别
- 代码位置热点

### 2. 性能分析

**检测内容：**
- 慢请求和操作
- 响应时间异常
- 资源耗尽迹象
- 超时模式

**输出：**
- 性能瓶颈识别
- 阈值违规
- 资源使用趋势
- 性能回归告警

### 3. 依赖分析

**检测内容：**
- 外部服务失败（API、数据库、缓存）
- 网络超时和连接问题
- 依赖健康度下降
- 级联故障模式

**输出：**
- 失败依赖识别
- 影响评估
- 超时/并发问题
- 服务依赖图

### 4. 业务逻辑分析

**检测内容：**
- 工作流失败
- 数据不一致
- 验证失败
- 状态机违规

**输出：**
- 业务流程中断
- 数据流问题
- 验证失败模式
- 状态转换问题

## 分析流程

### 阶段1：日志解析和规范化

1. **格式检测**
   - JSON日志（结构化）
   - 文本日志（非结构化）
   - 框架特定格式（Spring Boot、Django、Express等）
   - 通过正则表达式自定义模式

2. **字段提取**
   ```
   提取的通用字段：
   - 时间戳
   - 日志级别（TRACE、DEBUG、INFO、WARN、ERROR、FATAL）
   - 线程/进程ID
   - Logger/类名
   - 消息
   - 异常堆栈跟踪
   - MDC/上下文数据
   ```

3. **事件结构化**
   - 将时间戳规范化为UTC
   - 解析日志级别
   - 提取堆栈跟踪
   - 识别请求ID/关联ID
   - 分组多行事件

### 阶段2：异常检测

1. **统计分析**
   - 日志量激增
   - 错误率变化
   - 响应时间分布偏移
   - 频率异常检测

2. **模式识别**
   - 重复错误序列
   - 异常聚类
   - 失败循环
   - 时间模式

3. **基线对比**
   - 与正常时期对比（如果提供）
   - 识别偏差
   - 突出异常指标

### 阶段3：事件关联

1. **时间窗口分析**
   - 事故前上下文（之前发生了什么）
   - 事故时间线（事件序列）
   - 事故后影响评估（级联效应）

2. **因果链构建**
   - 通过关联ID链接相关事件
   - 构建依赖图
   - 识别触发事件
   - 追踪错误传播

3. **跨服务关联**（如果有多个日志）
   - 时间线同步
   - 请求旅程跟踪
   - 服务间通信分析

### 阶段4：根因假设

1. **证据收集**
   - 支持性日志条目
   - 指标和测量值
   - 错误频率
   - 时间线数据

2. **假设生成**
   ```
   对每个可能的根因：
   - 置信度（高/中/低）
   - 支持证据
   - 反驳证据
   - 受影响的组件
   - 业务影响
   ```

3. **根因评分**
   - 频率影响
   - 严重性影响
   - 时间相关性
   - 依赖深度
   - 业务影响权重

## 高级用法

### 自定义时间范围

```bash
# 分析特定事故窗口
/log-analyzer app.log --since "2025-01-29 14:30" --until "2025-01-29 15:45"
```

### 按关键词过滤

```bash
# 聚焦特定组件
/log-analyzer app.log --filter "PaymentService"

# 多个关键词
/log-analyzer app.log --filter "database,timeout,connection"
```

### 多个日志文件

```bash
# 跨服务关联
/log-analyzer api.log --correlate-with service.log,db.log

# 指定时间同步策略
/log-analyzer api.log service.log db.log --sync-by timestamp
```

### 基线对比

```bash
# 与正常时期对比
/log-analyzer incident.log --baseline normal.log --compare
```

### 导出分析

```bash
# 保存分析报告
/log-analyzer app.log --output report.md

# 导出为JSON
/log-analyzer app.log --output analysis.json --format json

# 导出时间线为CSV
/log-analyzer app.log --export-timeline timeline.csv
```

## 最佳实践

### 获得最佳结果

1. **提供充足的上下文**
   - 包含事故前、事故中、事故后的日志
   - 至少包含事故前30分钟和事故后15分钟
   - 更多数据 = 更好的关联分析

2. **包含所有相关服务**
   - API网关
   - 应用服务器
   - 数据库（慢查询日志）
   - 消息队列
   - 缓存

3. **保留日志级别**
   - DEBUG日志提供有价值的上下文
   - INFO日志显示正常流程
   - WARN/ERROR日志显示问题

4. **使用关联ID**
   - 跨服务请求跟踪
   - 用户旅程跟踪
   - 事务流分析

### 常见误区

**不要：**
- 只分析错误日志（缺少上下文）
- 忽略时间戳（无法关联）
- 过早过滤DEBUG日志（丢失上下文）
- 孤立分析（缺少依赖关系）

**要：**
- 包含相邻时间段
- 保留原始日志格式
- 如果可能，提供基线/正常时期的日志
- 分享系统上下文（负载、部署、配置变更）

## 示例场景

### 场景1：API中断

**输入：** 显示503错误的API网关日志

**分析：**
- 检测到：14:30-15:00期间100%错误率
- 根因：上游服务数据库连接池耗尽
- 证据：首次503前30秒出现连接超时错误
- 建议：扩展数据库，实施熔断器

### 场景2：内存泄漏

**输入：** 带有OutOfMemoryError的应用日志

**分析：**
- 检测到：崩溃前2小时出现内存警告
- 模式：堆使用量每小时增加5%
- 根因：缓存无限制增长
- 证据：GC日志显示内存恢复率下降
- 建议：实施缓存淘汰策略

### 场景3：性能缓慢

**输入：** 响应时间逐渐下降

**分析：**
- 检测到：p95响应时间从200ms增加到3秒
- 模式：与特定查询相关
- 根因：缺少数据库索引
- 证据：慢查询日志显示全表扫描
- 建议：在`orders.created_at`上添加索引

## 故障排除

### 问题："无法检测日志格式"

**解决方案：**
- 检查日志是否为二进制或压缩格式
- 尝试使用更小的日志样本
- 手动指定格式：`--format json|text|spring`

### 问题："未检测到异常"

**可能原因：**
- 时间范围未包含事故
- 日志级别过滤过于激进
- 问题存在于另一个服务
- 需要基线进行对比

### 问题："结果太多"

**解决方案：**
- 缩小时间范围
- 使用`--filter`聚焦特定组件
- 提高严重性阈值：`--min-level ERROR`
- 使用`--top N`限制结果数量
