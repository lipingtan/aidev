# 迭代优化规范

## 概述

本文档定义了游戏开发过程中三类迭代（Bug 修复、性能优化、玩法调优）的标准流程、完成条件和经验沉淀规则。

---

## 一、三类迭代定义

### 1.1 迭代类型总览

| 类型 | 触发条件 | 目标 | 优先级判定 | 典型耗时 |
|------|----------|------|-----------|----------|
| **Bug 修复** | 功能不符合设计预期 | 恢复正确行为 | P0(Crash)>P1(功能)>P2(体验)>P3(美观) | 0.5-4h |
| **性能优化** | 性能指标超出预算 | 达到性能预算标准 | 按影响范围和严重程度 | 2-8h |
| **玩法调优** | 玩法体验不达标 | 提升游戏手感/平衡 | 按影响玩家体验的程度 | 1-4h |

### 1.2 类型判定规则

```
问题出现
    │
    ├── 程序报错/崩溃/功能异常？ → Bug 修复
    │
    ├── 帧率低/加载慢/内存高？ → 性能优化
    │
    ├── 操作不舒服/数值不平衡/节奏不对？ → 玩法调优
    │
    └── 不确定？ → 先定位根因再分类
```

## 二、Bug 修复流程

### 2.1 标准流程

```
步骤 1: 复现确认
    ├── 记录复现步骤（精确到操作序列）
    ├── 确认复现率（必现/高概率/偶发）
    ├── 确认影响范围（单功能/多系统/全局）
    └── 判定优先级（P0-P3）

步骤 2: 根因定位
    ├── 阅读相关代码
    ├── 添加调试日志/断点
    ├── 缩小问题范围（二分法）
    └── 确认根本原因（不是表面现象）

步骤 3: 方案设计
    ├── 设计修复方案（可能有多个）
    ├── 评估副作用（是否影响其他功能）
    ├── 选择最小改动方案
    └── 如改动较大，需走门控确认

步骤 4: 实施修复
    ├── 按方案修改代码
    ├── 遵循代码规范（类型标注、中文注释等）
    ├── 单文件不超过 200 行
    └── 不引入新的技术债

步骤 5: 验证确认
    ├── 原始问题不再复现
    ├── 相关功能回归测试通过
    ├── 无新增问题
    └── 性能无明显退化
```

### 2.2 完成条件

| 检查项 | 标准 |
|--------|------|
| 问题复现 | 原始问题 100% 不再复现 |
| 回归测试 | 相关功能全部正常 |
| 代码规范 | 修改代码符合项目规范 |
| 无副作用 | 未引入新 Bug |
| 文档更新 | 迭代日志已记录 |

### 2.3 优先级定义

| 优先级 | 定义 | 响应时间 | 示例 |
|--------|------|----------|------|
| P0 - 致命 | 游戏崩溃/数据丢失/无法继续 | 立即处理 | Crash、存档损坏、死循环 |
| P1 - 严重 | 核心功能异常/流程阻断 | 当天处理 | 技能无效、任务无法完成、穿墙 |
| P2 - 一般 | 非核心功能异常/体验受损 | 本周处理 | UI 显示错误、音效缺失、动画异常 |
| P3 - 轻微 | 美观问题/极端情况 | 排期处理 | 文字重叠、极端操作下的异常 |

## 三、性能优化流程

### 3.1 标准流程

```
步骤 1: 性能分析
    ├── 使用 Godot Profiler 采集数据
    ├── 识别瓶颈（CPU/GPU/内存/IO）
    ├── 量化问题（当前值 vs 目标值）
    └── 确定优化优先级（影响最大的先处理）

步骤 2: 瓶颈定位
    ├── CPU 瓶颈：哪个函数/系统耗时最多
    ├── GPU 瓶颈：Draw Call/Shader/填充率/带宽
    ├── 内存瓶颈：哪类资产占用最多
    ├── IO 瓶颈：加载什么最慢
    └── 精确到具体代码行/资产/配置

步骤 3: 方案选择
    ├── 列出可选优化方案（至少 2 个）
    ├── 评估每个方案的：
    │   ├── 预期收益（提升多少）
    │   ├── 实施成本（改动量）
    │   ├── 风险（可能引入的问题）
    │   └── 可逆性（能否回退）
    └── 选择收益/成本比最高的方案

步骤 4: 实施优化
    ├── 按方案实施
    ├── 保留优化前的基准数据
    ├── 每个优化点独立提交（便于回退）
    └── 添加性能相关注释

步骤 5: 效果验证
    ├── 重新采集性能数据
    ├── 对比优化前后（量化改善）
    ├── 确认无功能退化
    ├── 确认在目标设备上达标
    └── 记录优化结果到迭代日志
```

### 3.2 完成条件

| 检查项 | 标准 |
|--------|------|
| 目标达成 | 优化后指标达到性能预算 |
| 无退化 | 功能行为未改变 |
| 可量化 | 有优化前后的对比数据 |
| 可回退 | 优化改动可独立回退 |
| 已记录 | 优化方案和结果已记录 |

### 3.3 常见优化手段速查

| 瓶颈类型 | 优化手段 | 预期收益 | 风险 |
|----------|----------|----------|------|
| CPU - 逻辑 | 减少 _process 调用频率 | 中 | 低 |
| CPU - 逻辑 | 使用对象池替代频繁实例化 | 高 | 低 |
| CPU - 物理 | 简化碰撞形状 | 中 | 中 |
| CPU - 物理 | 减少物理体数量（合并/禁用远处） | 高 | 中 |
| GPU - Draw Call | 合并网格 / 使用 MultiMesh | 高 | 低 |
| GPU - Draw Call | 减少材质种类 | 中 | 低 |
| GPU - 填充率 | 降低粒子数量/尺寸 | 中 | 低 |
| GPU - Shader | 简化 Shader 计算 | 中 | 中 |
| 内存 - 纹理 | 降低纹理分辨率 / 压缩 | 高 | 低 |
| 内存 - 纹理 | 使用纹理流式加载 | 高 | 中 |
| 内存 - 场景 | 分区加载/卸载 | 高 | 高 |
| IO - 加载 | 异步加载 + 加载界面 | 高 | 中 |
| IO - 加载 | 资源预加载 | 中 | 低（增加内存） |

## 四、玩法调优流程

### 4.1 标准流程

```
步骤 1: 问题识别
    ├── 明确"不好"的具体表现
    │   ├── 操作手感：延迟高/不跟手/不流畅
    │   ├── 数值平衡：太难/太简单/无挑战
    │   ├── 节奏问题：太快/太慢/无变化
    │   └── 反馈缺失：打击感弱/无成就感
    └── 量化问题（如可能）

步骤 2: 参考对标
    ├── 对比参考游戏的同类体验
    ├── 分析差异点
    └── 确定调优方向和目标

步骤 3: 参数调整
    ├── 识别影响体验的关键参数
    ├── 设计调整方案（通常是数值微调）
    ├── 优先调整导出变量（@export）
    └── 避免改动架构（调优不是重构）

步骤 4: 体验验证
    ├── 实际操作体验（不是看数据）
    ├── 对比调整前后的感受
    ├── 如有条件，请他人测试
    └── 反复微调直到满意

步骤 5: 固化记录
    ├── 记录最终参数值
    ├── 记录调优理由（为什么这个值好）
    ├── 更新设计文档中的数值
    └── 标记为"已调优"
```

### 4.2 完成条件

| 检查项 | 标准 |
|--------|------|
| 体验改善 | 主观体验明显优于调整前 |
| 参数合理 | 数值在合理范围内，无极端值 |
| 无副作用 | 未破坏其他系统的平衡 |
| 可复现 | 改善效果稳定，非偶然 |
| 已记录 | 参数变更和理由已记录 |

### 4.3 常见调优参数

| 系统 | 关键参数 | 调优方向 | 参考范围 |
|------|----------|----------|----------|
| 移动 | 加速度/最大速度/摩擦力 | 手感灵敏度 | 加速0.1-1.0s |
| 跳跃 | 跳跃力/重力/土狼时间 | 跳跃手感 | 土狼时间0.1-0.2s |
| 攻击 | 前摇/后摇/判定帧 | 打击节奏 | 前摇0.1-0.3s |
| 闪避 | 无敌帧/距离/冷却 | 风险回报 | 无敌帧0.2-0.5s |
| 伤害 | 基础伤害/倍率/暴击 | 战斗节奏 | 3-5刀击杀普通敌人 |
| 敌人AI | 攻击频率/反应时间/追击距离 | 难度感受 | 反应0.5-2.0s |
| 相机 | 跟随速度/偏移/FOV | 视觉舒适度 | 跟随0.1-0.3s延迟 |
| 打击感 | 顿帧时长/震动强度/击退距离 | 打击反馈 | 顿帧0.05-0.15s |

## 七、经验沉淀规则

### 7.1 沉淀触发条件

| 条件 | 动作 |
|------|------|
| 同类问题出现 **2 次以上** | 必须沉淀到案例库 |
| 解决方案具有通用性 | 建议沉淀 |
| 踩坑耗时超过 **2 小时** | 建议沉淀 |
| 涉及 Godot 引擎特殊行为 | 必须沉淀 |
| 涉及第三方工具/插件的坑 | 必须沉淀 |

### 7.2 案例库结构

```
AIDOC/global-info/knowledge/cases/
├── success/                    # 成功案例
│   ├── performance/            # 性能优化成功案例
│   ├── architecture/           # 架构设计成功案例
│   └── gameplay/               # 玩法设计成功案例
├── failure/                    # 失败案例（踩坑记录）
│   ├── godot-quirks/           # Godot 引擎特殊行为
│   ├── performance-traps/      # 性能陷阱
│   └── design-mistakes/        # 设计失误
└── README.md                   # 案例库索引
```

### 7.4 沉淀流程

```
迭代完成
    → 检查是否满足沉淀条件
    → 满足 → 撰写案例文档
    → 放入对应目录（success/ 或 failure/）
    → 更新 README.md 索引
    → 在相关知识库文件中添加引用链接
```

### 7.5 案例库使用规则

- 执行新任务前，检索案例库中是否有相关案例
- 遇到问题时，先查案例库再尝试解决
- 案例库中的方案优先于临时想出的方案
- 如果案例库方案不适用，记录原因并补充新案例
