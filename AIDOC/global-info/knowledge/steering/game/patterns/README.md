# 游戏设计模式 · 选择指南

> AI 在设计阶段（feature-development-flow 的"设计计划"步骤）根据本表选择模式。
> 每个模式的详细约束在对应 .md 文件中（按需创建）。

---

## 模式选择决策表

| 你要解决的问题 | 推荐模式 | 理由 | 本工作台约束 |
|---------------|----------|------|-------------|
| 角色/AI 有多种互斥行为状态 | **状态机** | 状态有限、转移条件明确 | 用代码 FSM，不用 AnimationTree 做逻辑；见 `state-machine.md` |
| 多个系统需要响应同一事件 | **观察者（EventBus）** | 解耦发送方和接收方 | 用全局 `EventBus` Autoload，不用节点间直连信号 |
| 实体由多种可组合能力构成 | **组件模式（ECS）** | 避免深继承，灵活组合 | 用 `gd_ecs` 插件的 Component + System |
| 频繁创建/销毁同类对象 | **对象池** | 避免 GC 压力和实例化开销 | 用 `ObjectPool` Autoload |
| 需要撤销/重做/录像回放 | **命令模式** | 操作可序列化、可回放 | 命令对象继承 RefCounted，不挂节点 |
| AI 需要复杂决策树（多层条件+并行） | **行为树** | 比 FSM 更适合深层嵌套决策 | 简单 AI 用 FSM 即可；3+ 层决策才上行为树 |
| 需要全局访问的管理器 | **单例（Autoload）** | Godot 原生支持 | 按 `godot-engine.md` 第七节顺序注册 |
| 数据驱动的配置（敌人/道具/技能表） | **数据资源（.tres）** | 策划可编辑，代码不硬编码 | 用 `@export` + Resource 子类 |

---

## 决策流程

```
设计一个新功能时：
    │
    ├── 有多种互斥状态？ → 状态机
    │
    ├── 需要跨系统通信？ → EventBus（观察者）
    │
    ├── 实体能力需要灵活组合？ → ECS 组件
    │
    ├── 同类对象频繁生灭？ → 对象池
    │
    ├── 操作需要可撤销/可回放？ → 命令模式
    │
    ├── AI 决策层级 ≥3 层？ → 行为树
    │
    └── 以上都不是？ → 直接写，不强加模式
```

---

## 组合使用规则

| 组合 | 场景 | 说明 |
|------|------|------|
| 状态机 + EventBus | 角色状态变化通知 UI/音效 | 状态切换时 emit 事件，UI 监听 |
| ECS + 对象池 | 子弹/粒子/临时实体 | Pool 管理实例，ECS 管理逻辑 |
| 状态机 + 行为树 | Boss AI | 顶层 FSM（阶段），每阶段内用行为树决策 |
| 命令 + EventBus | 战斗回放 | 命令执行后 emit 事件驱动表现 |

---

## 反模式（不要这样做）

| 反模式 | 问题 | 正确做法 |
|--------|------|----------|
| 所有通信都用 EventBus | 调试困难，事件满天飞 | 父→子直接调用；子→父/跨系统才用信号 |
| 2 个状态也上 FSM 类 | 过度设计 | bool 标志位即可 |
| 每个对象都池化 | 内存常驻浪费 | 只池化高频生灭对象（子弹、特效、伤害数字） |
| 用继承代替组件 | 3 层后无法维护 | 组合优于继承 |
| 行为树做简单巡逻 | 杀鸡用牛刀 | 2 状态 FSM 足够 |

---

## 何时创建新的模式文件

当以下条件满足时，按 `state-machine.md` 格式创建对应模式文件：
1. 项目中实际用到了该模式
2. 有本工作台特有的约束需要记录（如与 gd_ecs 的集成方式）
3. 踩过坑需要沉淀

不满足则不创建——AI 本身知道这些模式的通用实现方式。
