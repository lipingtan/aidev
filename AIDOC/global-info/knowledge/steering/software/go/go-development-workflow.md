# Go 软件开发工作流程

## 强制执行声明（对所有 AI 实体生效）

> **本规范对主代理、子代理、任何被委托的 AI 实体均具有约束力。**
> 子代理在执行任务时，必须遵循本文档定义的阶段门控和用户确认要求，不得以"已由上级代理确认"为由跳过确认步骤。

---

## CR 复杂度判定与流程要求

### 复杂 CR 定义（命中任一即为复杂）

1. 业务逻辑涉及多个条件分支或状态转换
2. 跨 ≥2 个模块（不同 app/ 子目录）的联动修改
3. 涉及数据库 DDL 变更 + 业务逻辑修改
4. 涉及权限/认证/多租户等安全相关变更
5. 新增完整 CRUD 接口（≥4 个端点）
6. 涉及第三方系统集成或异步流程

### 流程要求

| CR 类型 | 强制流程 |
|---------|---------|
| **复杂 CR** | 需求计划 → 用户确认 → 需求 → 设计计划 → 用户确认 → 设计 → 任务 → 执行 |
| **简单 CR** | 需求 → 设计 → 任务 → 执行（可合并计划到正式文档） |

**判定规则：** 不确定时按复杂 CR 处理。

**规范自演进：** 如果执行过程中遇到"按简单 CR 处理但实际踩坑（如频繁回退、遗漏依赖、跨模块副作用）"的案例，完成后自动将新判定条件追加到上述清单。

---

## 阶段门控规则（强制）

**核心原则：每个阶段的产出物必须经用户明确确认后，才能进入下一阶段。**

| 门控点 | 确认内容 | 未确认时禁止 |
|--------|----------|-------------|
| 需求计划完成 | AI 对需求的理解是否正确、澄清问题的答复 | 编写 requirements.md |
| 需求文档完成 | 用户故事/功能需求/验收标准是否完整准确 | 编写 design_plan.md |
| 设计计划完成 | 技术方案方向/设计问题的答复 | 编写 design.md |
| 设计文档完成 | API/数据库/核心逻辑/不变行为清单是否正确 | 编写 tasks.md |
| 任务列表完成 | 任务拆分/依赖顺序/验收标准是否合理 | 开始执行 |

**违反门控 = 流程错误，必须回退到未确认的阶段重新执行。**

## 角色定义

| 阶段 | 角色 |
|------|------|
| Requirement | 产品经理，擅长需求分析、用户故事、验收标准定义 |
| Design | Go 后端架构师，精通 Gin/GORM/go-admin 架构设计、API 设计、数据库设计 |
| Task | 技术项目经理，擅长任务拆解、依赖分析、并行规划 |
| 执行 | Go 高级开发工程师，精通 Go 1.21+、Gin、GORM、多租户架构 |
| Bugfix | 软件质量工程师，擅长缺陷分析、根因定位 |

## 1. Requirement 阶段

### 1.1 需求计划（requirements_plan.md）

**目的：** 确保 AI 正确理解用户意图，在编写正式需求前达成共识。

**流程：**
1. 创建 `requirements_plan.md`
2. **必须包含以下内容：**
   - **需求理解陈述**：用 AI 自己的话复述对需求的理解（目标、范围、预期效果）
   - **假设列表**：AI 做出的所有假设，标记 `[假设-N]`
   - **澄清问题**：用 `[Question-N]` 标签提出，创建空的 `[Answer-N]` 标签
   - **非功能性需求建议**：性能、安全、多租户隔离等
   - **影响范围预判**：预估涉及的模块和文件
3. 完成后请求用户审查
4. **用户必须：**
   - 确认或修正 AI 的理解陈述
   - 回答所有 `[Question]`
   - 确认或否决 `[假设]`
5. **全部确认后**，才进入 1.2

### 1.2 生成需求文档（requirements.md）

**前置条件：** requirements_plan.md 已获用户确认。

**流程：**
1. 基于确认后的计划，输出中文 `requirements.md`
2. 用户审查需求文档
3. 用户确认后，进入 Design 阶段

### 1.2 需求文档格式

```markdown
# 需求：{功能名称}

## 背景
{业务背景和目标}

## 用户故事
- 作为 {角色}，我希望 {功能}，以便 {价值}

## 功能需求
### FR-1: {需求名}
**描述：** ...
**验收标准：**
- WHEN {条件} THEN 系统 SHALL {行为}

## 非功能需求
- 性能：接口响应时间 < 200ms（P99）
- 安全：所有接口需 JWT 认证
- 多租户：数据按 tenant_id 隔离
```

## 2. Design 阶段

### 2.1 设计计划（design_plan.md）

**前置条件：** requirements.md 已获用户确认。

**流程：**
1. 创建 `design_plan.md`
2. **必须包含以下内容：**
   - **设计方向陈述**：基于需求，AI 阐述拟采用的技术方案方向
   - **技术选型理由**：为何选择特定方案（如有多种可行方案需列出比较）
   - **澄清问题**：用 `[Question-N]` 标签提出设计相关疑问
   - **风险点**：标识可能的技术风险或兼容性问题
3. 完成后请求用户审查
4. **用户必须确认设计方向和回答澄清问题后**，才进入 2.2

### 2.2 生成设计文档（design.md）

**前置条件：** design_plan.md 已获用户确认。

**流程：**
1. 基于确认后的设计计划，输出 `design.md`
2. 用户审查设计文档
3. 用户确认后，进入 Task 阶段

### 2.2 设计文档必须包含

```markdown
# 设计：{功能名称}

## 技术方案
### API 设计
| 方法 | 路径 | 描述 | 认证 |
|------|------|------|------|
| GET | /api/v1/game | 游戏列表 | JWT + 租户 |

### 数据库设计
```sql
-- 新增/修改的表结构
ALTER TABLE game ADD COLUMN xxx ...;
```

### 核心逻辑
{流程图或伪代码}

## 不变行为清单（回归防护）
| 编号 | 不变行为 | 验证方式 |
|------|----------|----------|
| RG-1 | 现有登录流程不受影响 | /login 接口正常返回 token |
| RG-2 | 租户隔离不被破坏 | 不同租户数据不互通 |

## 正确性属性
- 所有写操作必须记录 create_by/update_by
- 业务表查询必须带 tenant_id 过滤
```

**正确性属性自演进：** 每次设计 review 中发现遗漏的正确性属性模式（如"所有返回列表的接口必须排序"），追加到项目级正确性属性库（`AIDOC/project_doc/{project-name}/correctness-properties.md`），后续 design.md 自动引用。

## 3. Task 阶段

### 3.1 任务复杂度判定

按以下顺序匹配，命中即停：
1. 涉及跨模块调用或新增接口 → **高**
2. 涉及数据库 DDL 变更 → **高**
3. 涉及 ≥3 个文件的联动修改 → **中**
4. 有条件分支或业务规则判断 → **中**
5. 其余 → **低**

### 3.2 任务三要素格式

> 详细定义见 `go-task-representation.md`，以下为各复杂度的格式示例。

**高复杂度任务（示例）：**
```markdown
### Task N: {任务名}

**复杂度**: 高

**Scope（边界）:**
- 涉及文件: app/game/apis/game.go, app/game/service/game.go, app/game/service/dto/game.go
- 涉及模块: game
- 不触碰: common/middleware/tenant.go、其他域的 service

**Constraints（约束）:**
- 必须使用 middleware.GetTenantId(c) 获取租户 ID，不从请求参数读取
- 查询必须加 WHERE tenant_id = ? 过滤（tenant_id=0 时不过滤）
- 错误必须用 fmt.Errorf 包装并返回，不得忽略

> **约束知识库自演进：** 每个 CR 执行中发现的"必须遵守但容易遗忘的约束"（如某个中间件必须在另一个之后、某字段必须加 json:",string"），追加到项目级约束知识库（`AIDOC/project_doc/{project-name}/constraints-library.md`），后续 Task 生成时自动引用相关约束。

**Acceptance（验证标准）:**
- AC: 接口返回正确的分页数据
- AC: 不同租户数据互相隔离
- AC: go build ./... 零错误
- AC: 【回归】现有接口不受影响（RG-1）
```

**中复杂度任务（示例）：**
```markdown
### Task N: {任务名}

**复杂度**: 中

**Scope（边界）:**
- 涉及文件: app/game/models/game.go, app/game/service/dto/game.go
- 不触碰: 其他 model 文件

**Acceptance（验证标准）:**
- AC: Model 字段定义正确，包含 GORM tag
- AC: DTO 与 Model 字段对应
- AC: go build ./... 零错误
```

**低复杂度任务（示例）：**
```markdown
### Task N: {任务名}

**复杂度**: 低

**Acceptance:**
- AC: 修改内容符合需求描述
- AC: go build ./... 零错误
```

### 3.3 任务状态管理（强制）

**tasks.md 必须包含任务状态和进度信息。**

#### 状态定义

| 状态 | 标记 | 含义 |
|------|------|------|
| 未开始 | `⬜` | 任务尚未启动 |
| 进行中 | `🔨` | 正在执行 |
| 已完成 | `✅` | 已通过全部验收标准 |
| 阻塞 | `🚫` | 因依赖未满足而无法执行 |

#### tasks.md 顶部进度摘要（强制）

```markdown
## 执行进度

| 指标 | 值 |
|------|-----|
| 总任务数 | N |
| 已完成 | M |
| 进行中 | K |
| 未开始 | J |
| 完成率 | M/N (xx%) |
| 当前阶段 | Phase X: {阶段名} |
```

#### 每个任务标题格式

```markdown
### Task N: {任务名} ✅
### Task N: {任务名} 🔨
### Task N: {任务名} ⬜
```

#### 状态更新规则

1. **开始执行任务前**：将该任务状态从 `⬜` 改为 `🔨`，更新进度摘要
2. **任务通过全部验收后**：将状态从 `🔨` 改为 `✅`，更新进度摘要
3. **任务失败回退时**：将状态从 `🔨` 改回 `⬜`，在任务下方追加失败原因
4. **每完成一批任务后**：更新顶部进度摘要的计数和完成率
5. **并行执行多个任务时**：所有并行任务同时标为 `🔨`

#### 并行调度规则

任务可并行执行的条件：
- 无文件交叉（Scope 中涉及的文件无重叠）
- 无显式依赖关系（后序任务不引用前序任务的产出）
- 不在同一模块的同一层级（避免接口冲突）

在 tasks.md 中可以用 `依赖: Task N` 显式标注依赖关系：
```markdown
### Task 7: 用户-角色分配 ⬜
**依赖**: Task 5, Task 6
```

### 3.4 任务一致性自检（强制，tasks.md 生成后自动执行）

**触发条件：** tasks.md 首次生成或重大修改后，AI 必须自动执行以下检查，不需用户触发。

**检查维度：**

| # | 检查项 | 判定方法 |
|---|--------|----------|
| 1 | 需求覆盖度 | requirements.md 中每个 FR-N 的验收标准，在 tasks.md 中至少有一个 Task 的 Acceptance 对应覆盖 |
| 2 | 设计对齐度 | design.md 中 Handler 改动清单的每一行，在 tasks.md 中有对应 Task 覆盖 |
| 3 | 文件路径真实性 | tasks.md 中 Scope 涉及的文件路径在工程中实际存在（通过 list_directory/file_search 验证） |
| 4 | 回归覆盖 | design.md 不变行为清单中的每个 RG-N，在至少一个 Task 的 Acceptance 中被引用 |
| 5 | 内部一致性 | Task 之间的依赖关系无循环；并行 Task 无文件交叉 |
| 6 | 前后端对称性 | 后端接口改动有对应的前端调用改动 Task |

**执行流程：**
1. 逐条检查上表 6 项
2. 如发现问题，列出问题清单并自动修正 tasks.md（或反向修正 requirements/design）
3. 修正后输出简要报告（仅列修正项），不需用户确认
4. 如问题涉及需求/设计层面的矛盾（无法仅在 tasks 层面修正），则暂停并向用户报告

**示例输出格式：**
```
一致性自检通过 ✓（或：发现 N 个问题已自动修正）
- [修正] Task 5 Acceptance 补充 RG-2 回归验证
- [修正] Task 3 Scope 路径修正：xxx.go → yyy.go
```

**规范自演进：** 自检过程中如发现新类型的不一致（不在上述 6 项中），自动将其追加为第 7、8...项检查维度，确保后续 CR 自动覆盖。

## 4. Task 执行阶段

### 4.1 执行前（必须）

1. 读取任务的三要素（Scope/Constraints/Acceptance）
2. 确认涉及文件范围和禁区
3. 确认技术和行为约束
4. 三要素不完整时先澄清再执行
5. **更新 tasks.md 中该任务状态为 `🔨`**

### 4.2 执行中（必须）

1. 严格在 Scope 范围内操作
2. 遵循 Constraints 中的所有约束
3. 需要修改 Scope 之外的文件时，先报告用户确认

### 4.3 执行后（必须）

1. 运行 `go build ./...` 确认零错误
2. 运行 `go vet ./...` 确认无警告
3. 逐条验证 Acceptance 中的每个标准
4. **测试真实性检查**：逐条对照 tasks.md `自测` 部分，确认每个测试点都有对应的 Test 函数，且函数内确实验证了业务结果（非空测试/非仅 nil-check）
5. 全部通过后**更新 tasks.md 中该任务状态为 `✅`**
6. **更新顶部进度摘要**

## 5. 产品经理验收阶段（强制）

### 5.1 触发条件

当 tasks.md 中所有任务状态均为 `✅`（完成率 100%）时，自动进入产品经理验收阶段。

### 5.2 验收流程

```
所有任务完成 (100%)
    │
    ▼
自动触发产品经理 Review
    │
    ├── 以资深产品经理视角审查全部产出物
    │   • UI/UX 交互体验
    │   • 业务流程完整性
    │   • 数据展示合理性
    │   • 异常处理友好度
    │   • 操作效率与一致性
    │   • 前后端接口对齐性（5.2.1 强制检查）
    │
    ▼
生成验收报告（含问题清单 + 严重度分级）
    │
    ├── 问题数 ≤ 5 且无高优 → 当前 CR 内直接整改 → 标记验收通过
    │
    └── 问题数 > 5 或含高优 → 生成新 CR（UI/UX 优化 CR）→ 走完整流程
```

### 5.2.1 前后端接口对齐强制检查（逐项验证，违反即为高优问题）

| # | 检查项 | 判定方法 | 严重度 |
|---|--------|----------|--------|
| 1 | **字段名一致性** | 前端 TypeScript interface 的字段名 === 后端 JSON tag 名；不一致即为缺陷 | 高 |
| 2 | **字段类型一致性** | 前端 string/number/boolean 与后端 JSON 序列化后的实际类型匹配 | 高 |
| 3 | **树形组件 label/value 对齐** | el-tree/el-tree-select 的 `:props` 中 label/children/value 字段名必须与后端返回数据的字段名一致 | 高 |
| 4 | **列表/表格字段可见性** | 表格列 `prop` 值 === 后端返回对象的 JSON 字段名；不匹配则列显示为空 | 高 |
| 5 | **ID 字段不暴露给用户** | 编辑表单中不应让用户手动输入数字型自增 ID（如 tenant_id、user_id）；ID 应自动生成或从下拉/选择器获取 | 中 |
| 6 | **下拉选择器绑定值** | el-select 的 option value 必须用业务唯一标识（id/code），而非内部序号 | 中 |
| 7 | **显示名称 vs ID** | 页面展示区域（标题、面包屑、标签）必须显示人可读的名称（name/title），不得显示数字 ID | 中 |
| 8 | **API 路径前缀** | 所有前端 API 请求必须带 `/api/v1/` 前缀（确保被 vite proxy 代理）；裸路径（如 `/config`、`/menu`）视为缺陷 | 高 |
| 9 | **空数据防御** | 列表为空时不报错（需有空态提示）；对象为 null 时 computed 不崩溃（需 `?.` 安全访问） | 中 |
| 10 | **分页参数对齐** | 前端 page/page_size 命名 === 后端 query param 命名（不混用 pageNum/pageSize 和 page/page_size） | 中 |
| 11 | **雪花 ID 精度保护** | 后端 int64 雪花 ID 必须加 `json:",string"` tag；前端对应字段类型为 string；返回 ID 数组（如 getRoleResources）也用 string 类型 | 高 |
| 12 | **请求体结构对齐** | 前端发送的 JSON body 字段名和结构必须与后端 binding struct 完全一致（如 `resource_ids` vs `resourceIds`、`api_permission_ids` vs `api_ids`） | 高 |
| 13 | **关联查询返回业务字段** | 查询关联数据时（如用户已关联租户、角色已绑定应用），后端不应返回裸关联表记录（仅含 ID），应 JOIN 返回名称等业务字段供前端展示 | 中 |
| 14 | **批量操作兼容性** | 前端穿梭框/批量操作发送 ID 数组时，后端必须支持批量（如 `tenant_ids: [...]`）；前端发字符串数组、后端需解析为 int64（使用 StringInt64Slice 等自定义类型） | 中 |
| 15 | **乐观锁 version 传递** | 编辑操作必须携带当前数据的 version 字段；前端列表/详情接口返回中必须包含 version；编辑表单 submit 时必须传递 version | 高 |

**执行方式：**
- AI 在产品验收阶段，逐个打开前端 API 模块（`src/api/*.ts`）和对应 Vue 组件，对照后端 handler/model 的 JSON tag 做交叉检查
- 任何不匹配项立即记录到验收报告并标记严重度
- 高优问题必须在当前 CR 内修复后才能标记验收通过
- **规范自演进（强制）：** 每次 review 完成后，如果发现了不在上述清单中的新问题模式，必须立即将其追加到本检查清单中（附编号、判定方法、严重度），确保同类问题在后续 CR 中被自动检测到

### 5.3 任务验收状态

tasks.md 中每个任务在开发完成后（`✅`）还需标注**产品验收状态**：

| 标记 | 状态 | 含义 |
|------|------|------|
| `📋` | 待验收 | 开发完成，等待产品经理 Review |
| `🎯` | 验收通过 | 产品经理确认符合预期 |
| `🔄` | 需整改 | 产品经理提出修改意见，待修复 |

**标题格式扩展：**
```markdown
### Task N: {任务名} ✅ 📋        # 开发完成，待验收
### Task N: {任务名} ✅ 🎯        # 开发完成 + 验收通过
### Task N: {任务名} ✅ 🔄        # 开发完成但需整改
```

### 5.4 验收报告格式

```markdown
## 产品经理验收报告

**验收时间**: YYYY-MM-DD
**验收结论**: 通过 / 需整改 / 生成新 CR

### 问题清单

| # | 严重度 | 页面/模块 | 问题描述 | 建议方案 | 处理方式 |
|---|--------|-----------|----------|----------|----------|
| 1 | 高 | ... | ... | ... | 当前CR整改 / 新CR |

### 判定规则
- 高优：影响核心流程或数据安全
- 中优：影响用户效率或体验一致性
- 低优：美观/文案/非阻塞性体验
```

### 5.5 强制规则

- 所有任务 100% 完成后**必须触发**产品验收，不得跳过
- 验收未通过的任务不得标记为最终完成
- 新 CR 遵循正常流程（需求计划 → 需求 → 设计 → 任务 → 执行）
5. 回归验证项无法自动验证时，标注"需人工确认"

## 5. Bugfix 流程

### 5.1 文件存放位置

```
AIDOC/project_doc/{project-name}/Fix-{N}-{bug简述}/
├── bugfix.md       # bug 分析文档
├── design.md       # 修复设计
└── tasks.md        # 修复任务
```

### 5.2 Bugfix 文档格式

```markdown
# Bugfix: {bug 简述}

## Bug 分析
**当前行为（缺陷）：**
WHEN {触发条件} THEN 系统 {错误表现}

**期望行为（正确）：**
WHEN {触发条件} THEN 系统 SHALL {正确行为}

**不变行为（回归防护）：**
WHEN {相关场景} THEN 系统 SHALL CONTINUE TO {保持行为}

## 根因分析
{定位到具体文件和代码行}

## 影响范围
{涉及的模块、接口、数据}
```

### 5.3 Go 常见 Bug 排查清单

**第一优先级：基础设施层**
1. **JSON 反序列化问题**
   - `time.Time` 字段格式不匹配
   - 指针类型 vs 值类型（`*int` vs `int`）
   - 枚举值不在预期范围内

2. **中间件链问题**
   - JWT 验证失败（token 格式、过期）
   - 租户 ID 未正确注入（`WithTenantId` 中间件顺序）
   - 数据库连接未初始化（`WithContextDb` 中间件）

**第二优先级：业务逻辑层**
3. **nil pointer dereference**
   - 数据库查询结果未判空
   - 接口类型断言失败
   - 未初始化的 map/slice

4. **GORM 查询问题**
   - 忘记加 `tenant_id` 过滤
   - 软删除字段未正确配置
   - 事务未正确提交/回滚

**规范自演进：** 每次 Bugfix 完成后，如果根因不在上述排查清单中，自动将新根因类型追加到对应优先级下，供后续排查参考。
