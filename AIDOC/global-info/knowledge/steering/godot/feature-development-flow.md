# 功能开发流程规范

> 定义单个功能/模块从需求到上线的标准化流程。
> 适用于 Phase 2-4 中每个具体功能的开发（如"实现锁定系统"、"实现对话系统"）。
> 与 `execution-protocol.md` 的 PRE/POST-CHECK 配合使用。

---

## 一、流程总览

```
需求计划 → 需求确认 → 设计计划 → 设计确认 → 任务拆解 → 任务执行 → 集成验证
```

每个阶段有明确的产出物和门控条件，未通过门控不得进入下一阶段。

---

## 二、阶段详细定义

### 2.1 需求计划

**目标**：明确功能要做什么、为谁做、边界在哪。

**产出物**：功能需求卡（写入对应设计文档或独立 `.md`）

**需求卡模板**：
```markdown
## 功能需求：{功能名}

### 概述
一句话说明该功能的核心价值。

### 用户故事
作为 [角色]，我希望 [行为]，以便 [价值]。

### 功能边界
- 包含：[明确做什么]
- 不包含：[明确不做什么]
- 依赖：[前置功能/系统]

### 验收标准（粗粒度）
- [ ] 标准 1
- [ ] 标准 2
```

**门控**：需求卡已填写完整，用户确认"做什么"无歧义。

---

### 2.2 需求确认

**目标**：消除歧义，锁定范围。

**活动**：
- 检查需求与 GDD/架构文档是否冲突
- 检查与已有系统的接口兼容性
- 确认优先级和依赖顺序

**门控**：用户明确确认需求，标记为"已确认"。

---

### 2.3 设计计划

**目标**：确定技术方案——用什么数据结构、什么模式、怎么与现有系统交互。

**产出物**：技术设计摘要

**设计摘要模板**：
```markdown
## 技术设计：{功能名}

### 架构方案
- 采用模式：[状态机/组件/观察者/...]
- 核心类/脚本：[列出将创建的文件]
- 数据结构：[关键数据定义]

### 接口定义
- 对外暴露的 API/信号
- 依赖的外部接口

### 与现有系统的交互
- 读取：[从哪些系统获取数据]
- 写入：[向哪些系统发送事件/修改数据]

### 文件清单
| 文件路径 | 职责 | 预估行数 |
|----------|------|----------|
| ... | ... | ≤200 |
```

**门控**：设计方案无架构冲突，用户确认技术方向。

---

### 2.4 设计确认

**目标**：锁定技术方案，确保不会在实现中途推翻。

**活动**：
- 检查设计是否符合代码生成规范
- 检查是否超出单文件 200 行限制（需拆分）
- 检查是否引入循环依赖

**门控**：用户确认设计，标记为"已确认"。

---

### 2.5 任务拆解

**目标**：将设计拆解为可独立执行和验证的最小任务单元。

**规则**：
- 每个任务必须包含三要素（见第三节）
- 单个任务产出 1-3 个文件
- 任务间依赖关系明确
- 任务粒度：1-4 小时可完成

**产出物**：任务列表（含依赖图）

**门控**：任务列表覆盖设计中所有文件，无遗漏。

---

### 2.6 任务执行

**目标**：按任务列表逐个实现。

**执行规则**：
1. 执行前：读取任务三要素，确认依赖文件存在
2. 执行中：严格在 Scope 范围内操作，遵循 Constraints
3. 执行后：逐条验证 Acceptance，全部通过才标记完成

**门控**：每个任务通过代码级 POST-CHECK（见 `execution-protocol.md` 第五节）。

---

### 2.7 集成验证

**目标**：验证功能与现有系统协同工作。

**活动**：
- 功能可在编辑器中独立运行
- 与依赖系统联调无报错
- 性能无明显退化
- 信号/事件正确触发和响应

**门控**：集成验证通过，功能标记为"已完成"。

---

## 三、任务三要素

每个 Task 必须包含：

| 要素 | 定义 | 说明 |
|------|------|------|
| **Scope（范围）** | 涉及哪些文件、系统、数据 | 明确边界，防止越界修改 |
| **Constraints（约束）** | 必须遵循的规范和限制 | 代码规范、架构约束、性能预算 |
| **Acceptance（验收标准）** | 怎么算完成 | 可逐条勾选的检查清单 |

### 复杂度分级

| 复杂度 | 典型场景 | 三要素要求 |
|--------|----------|-----------|
| **低** | 数据填充、参数调整、单文件修改 | 只需 Acceptance |
| **中** | 新增组件/系统、实现单个子功能 | Scope + Acceptance |
| **高** | 多文件协作系统、跨系统集成 | 完整三要素 |

### 任务格式示例

**高复杂度**：
```markdown
### Task: 实现伤害计算系统

**复杂度**: 高

**Scope:**
- 创建文件: systems/combat/damage_system.gd
- 涉及系统: StatsSystem（读取属性）、BuffSystem（读取增减益）、EventBus（发送事件）
- 不触碰: 角色控制器、UI 系统

**Constraints:**
- 继承 EcsSystem 基类
- 单文件 ≤200 行
- 伤害公式: final = (base_atk - def) * element_mult * crit_mult
- 无敌帧期间跳过计算
- 所有参数有类型标注

**Acceptance:**
- [ ] 文件创建且语法无错误
- [ ] 伤害公式计算结果正确
- [ ] 无敌帧检查生效
- [ ] 元素克制倍率正确应用
- [ ] damage_dealt 事件通过 EventBus 发送
- [ ] 文件头注释包含依赖说明
```

**中复杂度**：
```markdown
### Task: 实现经验值组件

**复杂度**: 中

**Scope:**
- 创建文件: systems/growth/experience_component.gd
- 涉及系统: EventBus（监听 enemy_killed）

**Acceptance:**
- [ ] 组件可挂载到 Entity
- [ ] add_exp() 正确累加经验
- [ ] 达到阈值时发出 level_up_ready 信号
- [ ] 经验阈值按成长曲线计算
```

## 四、流程简化规则

| 场景 | 可跳过的阶段 | 说明 |
|------|-------------|------|
| 已有明确设计文档 | 需求计划+确认 | 直接从设计计划开始 |
| 简单数据填充 | 设计计划+确认 | 直接拆任务执行 |
| Bug 修复 | 需求+设计 | 按 `iteration-workflow.md` 流程 |
| 用户明确说"直接做" | 需求确认+设计确认 | 跳过确认等待，但仍需产出需求卡和设计摘要 |
| **蓝图覆盖的标准功能** | 需求计划+设计计划 | AI 按蓝图+模板自动生成需求和设计，人类只需批准 |

## 五、AI 推荐 + 人类批准模式

> 适用于无经验用户。AI 承担"评审者"角色，人类只做最终拍板。

### 5.1 需求阶段

AI 行为：
1. 根据游戏类型加载 `game-type-blueprints.md` 对应蓝图
2. 展示功能清单，标注推荐优先级
3. 给出明确建议："建议本阶段实现 X、Y、Z，原因是..."

人类行为：
- 同意 → 进入设计
- 调整 → 增删功能项后确认
- 不确定 → AI 进一步解释每个功能的作用

### 5.2 设计阶段

AI 行为：
1. 加载对应系统模板（`templates/rpg/` 或 `templates/action/`）
2. 生成设计方案，包含：
   - 推荐方案（标注为 ⭐）
   - 替代方案（如有）
   - 风险提示
3. 用一句话总结："推荐方案 A，因为..."

人类行为：
- 同意推荐 → 进入任务拆解
- 选择替代 → AI 按替代方案继续
- 看不懂 → AI 用类比解释（"类似 XX 游戏的做法"）

### 5.3 验收阶段

AI 行为：
1. 执行代码级 POST-CHECK（自动）
2. 对照 `experience-benchmarks.md` 检查参数是否在合理范围
3. 给出体验评估："当前攻击前摇 0.15s，在推荐范围内（0.08-0.2s），偏灵敏风格"

人类行为：
- 实际操作体验
- 反馈"太快/太慢/刚好"
- AI 根据反馈调整参数

### 5.4 自动执行模式

当以下条件同时满足时，AI 可跳过确认直接执行：
- 功能在蓝图库中有对应条目
- 模板库中有完整实现模板
- 用户未对该功能提出特殊要求
- 用户已开启"自动执行"偏好

自动执行后仍需输出摘要："已完成 [功能名]，采用标准模板，参数使用默认推荐值。"
