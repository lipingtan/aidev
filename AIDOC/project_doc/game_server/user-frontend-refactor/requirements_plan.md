# 需求计划：plugin-architecture（插件化架构规范）

## 需求理解

将整个前后端系统从"单体前端 + 固定业务模块"升级为"最小平台框架 + 插件化扩展"架构。

- 目标：定义前后端插件化架构规范（插件接口协议、加载机制、路由注册、构建方式），为后续分步实施提供基础
- 范围：dev-web-admin、dev-web-user、Go 后端 三端的插件化架构设计
- 预期效果：
  - 框架只包含最小核心功能（用户体系 + 权限 + 多租户 + 插件管理）
  - 所有业务功能通过插件安装/卸载
  - 插件支持独立构建打包（运行时加载）和源码按需编译两种模式
  - 用户端同时支持 PC 和 H5 端

## 框架内置功能清单

### 管理端（dev-web-admin）框架内置

| 模块 | 说明 |
|------|------|
| 用户管理 | 用户 CRUD、密码重置、状态管理 |
| 角色管理 | 角色 CRUD、权限分配 |
| 菜单/权限管理 | 菜单树管理、权限 code 管理 |
| 多租户管理 | 租户 CRUD、租户配额、数据隔离 |
| 插件管理 | 插件注册/启用/禁用/卸载、插件配置 |
| 系统配置 | 系统参数、全局开关 |
| 操作日志 | 登录日志、操作日志 |
| 个人中心 | 个人信息、修改密码 |

### 用户端（dev-web-user）框架内置

| 模块 | 说明 |
|------|------|
| 注册/登录 | 账号注册、登录、Token 管理 |
| 个人信息 | 头像、昵称、密码修改 |
| 插件页面容器 | 动态加载插件提供的用户侧页面 |

### 后端框架内置

| 模块 | 说明 |
|------|------|
| 认证/授权 | JWT、RBAC |
| 多租户 | 数据隔离中间件 |
| 插件生命周期 | 注册、加载、路由挂载、卸载 |
| 基础 CRUD | 用户/角色/菜单/租户/配置/日志 |

### 所有其他功能 → 插件

示例：部门管理、岗位管理、字典管理、定时任务、服务监控、接口管理、代码生成、Swagger 等。

## 假设列表

- [假设-1] 后端插件 SDK 已有基础（`plugin-sdk/`），本次重点定义前端插件协议和前后端联动规范
- [假设-2] 前端插件的独立构建产物为 ES Module 格式（`/static/plugins/{name}/index.js`）
- [假设-3] 插件可以注册：路由、菜单项、API 接口、Store 模块、全局组件
- [假设-4] 多租户维度隔离插件可见性（不同租户可安装不同插件）
- [假设-5] admin-frontend-refactor 中已实现的模块（部门/岗位/字典/配置/定时任务/监控/接口/开发工具）后续将拆为插件，但当前 CR 不执行拆分，只定义规范
- [假设-6] dev-web-user 的 PC/H5 适配方案在本 CR 中一并定义

## 澄清问题

- [Question-1] 插件的权限控制粒度：插件安装后，其菜单/按钮权限是自动注册到权限系统（插件自带权限声明），还是需要管理员手动配置？
  [Answer-1] 自动注册，插件自带权限声明（manifest 中定义 permissions 列表），安装时自动注册到权限系统。
- [Question-2] 插件间通信：不同插件之间是否需要数据共享或事件通信？如果需要，通过什么机制（EventBus/共享 Store/插件 API）？
  [Answer-2] 采用方案 1：框架提供共享上下文（只读全局状态）+ EventBus（松耦合事件通信）+ 扩展点（插件向框架注册内容）。插件之间不直接互相调用。

- [Question-3] 插件版本管理：是否需要支持插件升级、回滚？还是只做简单的安装/卸载？
  [Answer-3] 支持升级和回滚。
- [Question-4] dev-web-user 的 UI 框架选型：当前用 Vant（移动端），PC 端用什么？Element Plus？还是用一个同时支持 PC/H5 的方案（如 NutUI、Tailwind CSS 响应式）？
  [Answer-4] 采用方案 C：Vant + 响应式增强。H5 端继续用 Vant，PC 端对同一页面做响应式拉宽（CSS Grid/Flex），Vant 4 桌面端适配已足够。对于个别需要复杂 PC 交互的插件页面，插件内部自行引入 Element Plus。
- [Question-5] 插件的前端源码按需编译模式：是将插件源码放在主项目的 `src/plugins/` 目录下，还是通过 monorepo workspace 引用外部包？
  [Answer-5] 放主项目 `src/plugins/` 子目录，跟随主项目一起编译。后续规模增大需独立发布时再迁移至 monorepo。

- [Question-6] admin-frontend-refactor 刚完成的实现（部门/岗位/字典等模块代码在 dev-web-admin 中）：这些代码暂时保持现状（框架内），等架构规范定义好后再拆为插件？
  [Answer-6] 暂保持现状，等插件化架构规范和 SDK 就绪后再拆为插件。

- [Question-7] 集群部署下的插件状态一致性：如果后端多实例部署（如 K8s 多 Pod），插件注册/安装/卸载操作如何保证所有实例状态一致？
  [Answer-7] 采用方案 A：DB 为真相源 + 启动时全量加载 + Redis Pub/Sub 广播变更通知。初期单实例只做"DB + 启动加载"，预留广播接口，集群部署时接入 Redis。
## 非功能需求建议

- **插件隔离**：插件的 CSS/全局变量不能污染框架和其他插件
- **按需加载**：未启用的插件代码不加载，不影响首屏性能
- **热插拔**：管理端启用/禁用插件后，前端菜单实时更新（无需刷新页面或重新部署）
- **类型安全**：插件 SDK 提供 TypeScript 类型定义，开发时有完整类型提示
- **开发体验**：插件开发时支持 HMR，不需要每次重新构建整个项目

## 影响范围预判

- 涉及项目：dev-web-admin、dev-web-user、Go 后端（plugin-sdk）
- 涉及文件：
  - 前端：src/plugins/（新增插件 SDK）、src/router/（动态注册）、src/layout/（插件菜单注入）
  - 后端：plugin-sdk/（扩展前端协议）
- 可能的副作用：
  - 需要重新设计菜单注册机制（从静态路由 → 动态合并）
  - 可能需要引入微前端或 Module Federation 技术
  - dev-web-user 如果要支持 PC 端，布局层需要重构
