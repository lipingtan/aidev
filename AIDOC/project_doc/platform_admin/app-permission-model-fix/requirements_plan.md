# 需求计划：应用-权限归属模型修正

## 需求理解

- 目标：明确菜单和 API 权限归属于应用的两层配置模型，修正当前实现中缺失的"应用能力定义"层
- 当前问题：菜单/API 权限直接与租户绑定（`tenant_id` 隔离），没有清晰的"应用拥有哪些菜单/API"的元配置层；角色分配权限时没有按应用分组
- 预期效果：
  - 第一层（元配置）：应用管理界面中可定义该应用包含哪些菜单和 API
  - 第二层（授权）：角色分配权限时，先选应用再在该应用范围内勾选菜单/API

## 假设列表

- [假设-1] `admin_resource` 和 `admin_api_permission` 已有 `app_code` 字段，可作为归属应用的标识
- [假设-2] 当前数据模型不需要新增表，只需要：
  - 界面上明确应用→菜单/API 的管理入口
  - 角色权限分配时按应用分 Tab 或分组展示
- [假设-3] 资源和 API 权限的 `tenant_id` 保留（表示在哪个租户下生效），`app_code` 表示归属哪个应用

## 澄清问题

- [Question-1] 菜单/API 的元配置是"全局定义一次，所有订阅了该应用的租户共享"，还是"每个租户独立维护自己应用下的菜单/API"？
  [Answer-1]
应用的菜单和api是全局的,平台管理元可以管理这个配置，而租户管理员只能只读
- [Question-2] 角色分配权限的界面交互：是把所有已订阅应用的菜单合并显示（按 app 分组），还是先选一个应用再展示该应用的权限树？
  [Answer-2]
按每个应用去设置权限，平台管理员有所有应用的配置权限的权限，租户管理员只能按订阅的app来设置权限
- [Question-3] 应用管理界面是否需要一个"菜单管理"Tab 和 "API管理" Tab 来配置该应用的元数据（哪些菜单/API 属于这个应用）？还是在独立的菜单管理/API权限管理页面通过 app_code 过滤？
  [Answer-3]
在应用管理里面去做菜单管理/API权限（类似平台超级管理员哪种方式，左侧一个列表，选中一个应用后，
右侧有菜单和api的管理；独立的菜单管理这个待定，感觉是冗余的，可以先隐藏
## 影响范围预判

**后端可能改动：**
- 角色权限分配接口加 app_code 过滤逻辑
- GetUserMenu 按角色绑定的应用过滤菜单

**前端改动：**
- 角色详情页的菜单权限 Tab / API 权限 Tab 增加应用选择器或按应用分组
- 应用管理界面可能增加"管理菜单"/"管理API"入口

## 非功能需求建议

- 保持向后兼容：如果 app_code 为空的菜单/API 视为"平台级"，所有应用共享
