# 设计计划：激活码激活+app内购买

## 设计方向

基于确认的需求，拟采用以下技术方案：

1. **激活码管理**：复用现有 license 插件的激活码管理功能，新增设备绑定表（activation_code_devices）
2. **app内购买**：新增购买接口（/api/v1/user/auth/license/purchase），调用微信支付统一下单API（H5支付）
3. **支付回调**：新增支付回调接口（/api/v1/user/auth/license/payment/callback），接收微信支付回调
4. **订单管理**：新增订单表（license_orders），记录购买订单状态
5. **设备绑定**：激活时记录设备ID，激活码已绑定的设备才能激活（或解绑后重新绑定）

## 技术选型

### 数据库设计

| 选项 | 优点 | 缺点 | 推荐 |
|------|------|------|------|
| 新增 activation_code_devices 表 | 清晰记录设备绑定关系 | 需要新增表 | ✓ |
| 在 activation_codes 表中新增 device_id 字段 | 简单 | 无法记录解绑历史 | ✗ |

### 支付流程

| 选项 | 优点 | 缺点 | 推荐 |
|------|------|------|------|
| 微信H5支付 | 不需要集成SDK，实现简单 | 需要跳转微信，体验稍差 | ✓（用户指定） |
| 微信APP支付 | 用户体验好 | 需要集成SDK | ✗ |

## 澄清问题

- [Question-1] 订单表的 tenant_id 如何处理？
  - 业界最佳实践：订单表包含 tenant_id，按租户隔离数据。
  - 推荐答案及理由：订单表包含 tenant_id，按租户隔离数据。理由：与现有架构一致。
  [Answer-1]

- [Question-2] 微信支付回调的 notify_url 如何配置？
  - 业界最佳实践：notify_url 配置在服务端，每个商户一个固定的回调URL。
  - 推荐答案及理由：notify_url 配置在服务端，固定的回调URL。理由：微信支付要求固定的回调URL。
  [Answer-2]

- [Question-3] 激活码生成规则？

  - 推荐答案及理由：随机生成16位字母数字组合，格式 XXXX-XXXX-XXXX-XXXX。理由：与现有激活码生成规则一致。
  [Answer-3]

## 风险点

- [Risk-1] 微信支付H5支付需要在微信开放平台申请权限，可能需要时间
- [Risk-2] WebView中打开支付链接可能受到浏览器兼容性影响
- [Risk-3] 支付回调可能延迟或失败，需要处理超时和重试
