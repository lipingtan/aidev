# 需求计划：激活码激活+app内购买

## 需求理解

- **目标**：支持通过激活码激活游戏，支持用户在app内通过微信支付购买激活码后直接激活，一个激活码最多只能激活一个设备（防止多人共用）
- **范围**：
  - 后端：license 插件（激活码管理、设备绑定、购买接口）
  - 前端：mjarch flavor（激活页面、购买流程）
- **预期效果**：
  - 用户可以输入激活码激活游戏
  - 用户可以在app内通过微信支付购买激活码并自动激活
  - 一个激活码最多只能在一个设备上使用，防止多人共用

## 假设列表

- [假设-1] 激活码与设备绑定，一个激活码只能在一个设备上使用
- [假设-2] app内购买流程：用户点击购买 → 微信支付 → 支付成功 → 服务端生成激活码并直接激活 → 返回激活结果
- [假设-3] 淘宝购买流程：用户淘宝下单 → 获得激活码 → 在app中输入激活码激活
- [假设-4] 激活码一次性使用，激活后状态变为"已使用"

## 澄清问题

- [Question-1] 激活码与设备绑定后，用户换设备后能否继续使用？
  - 业界最佳实践：激活码与设备绑定后，用户换设备需要重新购买或联系客服解绑。部分产品支持在"我的设备"页面解绑旧设备后绑定新设备（有限次数）。
  - 推荐答案及理由：支持在"我的设备"页面解绑旧设备后绑定新设备（每个激活码最多解绑3次）。理由：给用户一定的灵活性，同时防止频繁换设备滥用。
  [Answer-1]
支持在"我的设备"页面解绑旧设备后绑定新设备（每个激活码最多解绑3次）。理由：给用户一定的灵活性，同时防止频繁换设备滥用
- [Question-2] app内购买的价格由谁决定？
  - 业界最佳实践：价格由服务端配置，app端从服务端获取价格。
  - 推荐答案及理由：价格由服务端配置，app端从服务端获取价格。理由：方便运营调整价格，无需更新app。
  [Answer-2]
价格由服务端配置，app端从服务端获取价格。
- [Question-3] 微信支付由谁实现？
  - 业界最佳实践：app端集成微信支付SDK，服务端生成支付订单并返回支付参数。
  - 推荐答案及理由：app端集成微信支付SDK，服务端生成支付订单并返回支付参数。理由：标准的微信支付流程。
  [Answer-3]
使用微信H5支付。app端在WebView中打开支付链接，用户完成支付后服务端接收回调并激活。
- [Question-4] 支付成功后，激活码如何生成和激活？
  - 业界最佳实践：支付成功后，服务端生成激活码并直接激活（无需用户输入），返回激活结果给app端。
  - 推荐答案及理由：支付成功后，服务端生成激活码并直接激活，返回激活结果给app端。理由：简化用户操作，提升用户体验。
  [Answer-4]
支付成功后，服务端生成激活码并直接激活（无需用户输入），返回激活结果给app端。
- [Question-5] 激活码的有效期？
  - 业界最佳实践：激活码有有效期（如30天），过期后不能使用。
  - 推荐答案及理由：激活码有有效期（30天），过期后不能使用。理由：防止激活码长期囤积。
  [Answer-5]
激活码有效期在服务端做一下定义，创建完成后多长时间有效
- [Question-6] 激活成功后，用户获得什么？
  - 业界最佳实践：用户获得会员身份（如VIP会员），可以访问VIP游戏。
  - 推荐答案及理由：用户获得会员身份（如VIP会员），可以访问VIP游戏。理由：与现有会员体系一致。
  [Answer-6]
用户获得激活码上定义的会员等级比如VIP会员。
- [Question-7] 会员有效期？
  - 业界最佳实践：会员有有效期（如365天），过期后需要重新激活。
  - 推荐答案及理由：会员有有效期（365天），过期后需要重新激活。理由：与现有会员体系一致。
  [Answer-7]
会员有有效期（如365天），过期后需要重新激活
## 非功能需求建议

- 性能：激活接口响应时间 < 500ms（P99）
- 安全：激活码随机生成，防止猜测；支付订单防重放
- 多租户：数据按 tenant_id 隔离
