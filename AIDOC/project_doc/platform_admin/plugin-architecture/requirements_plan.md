# 需求计划：SaaS 底座插件架构

## 背景

将当前 platform_admin 工程抽象为 SaaS 服务脚手架底座，基础能力（用户/角色/菜单/字典/租户/权限）作为 Host，新功能模块通过插件机制扩展。插件参考 hashicorp/go-plugin（gRPC over stdio），同时提供前后端实现。

## 澄清问题

[Question] Q1: 插件的粒度——当前的 game 模块（游戏/DLC/玩家/订单/支付/H5）整体作为一个插件，还是每个子模块各自独立为插件？
[Answer]
game 模块整体作为一个插件，saas底座功能里面需要有对插件的管理功能
[Question] Q2: 插件是否需要热加载（运行时启停），还是只支持启动时加载？hashicorp/go-plugin 支持运行时启停，但复杂度更高。
[Answer]
需要支持运行时启停

[Question] Q3: 插件前端的加载方式——是打包为独立 JS bundle（类似微前端 qiankun/wujie），还是编译时合并（monorepo 方式）？前者支持独立部署但复杂，后者简单但需要重新构建。
[Answer]
后者简单但需要重新构建，指的什么？
[Question] Q4: 插件是否需要独立数据库（每个插件自己的表），还是共享 Host 的数据库（插件通过 Host 提供的 DB 连接操作）？
[Answer]
插件默认使用host的数据库，但是表名需要通过插件名隔离
[Question] Q5: 插件之间是否需要通信（插件 A 调用插件 B 的能力），还是只与 Host 交互？
[Answer]
需要可以支持插件之间通信通信

[Question] Q6: 这个改造是渐进式的（先搭框架，game 模块暂时保留在 Host 内，后续再抽离为插件），还是一步到位（立即把 game 模块抽离为插件）？
[Answer]
先搭建框架

[Question] Q7: 插件的分发方式——是本地目录放置二进制文件，还是需要插件市场/远程下载机制？
[Answer]
远程下载或者目录上传都需要支持

## 非功能性需求（待确认）

- 性能：插件 gRPC 调用延迟对 API 响应时间的影响是否可接受？（预估增加 1-5ms） 可以
- 安全：插件进程是否需要沙箱隔离（限制文件系统/网络访问）？按最佳实践来，保持一定灵活性
- 稳定性：插件崩溃是否影响 Host？（go-plugin 默认进程隔离，插件崩溃不影响 Host）不影响
- 开发体验：是否需要提供插件开发脚手架/CLI 工具？需要
