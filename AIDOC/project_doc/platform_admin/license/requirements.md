# License 插件 - 需求文档

## 项目背景
为 mjarch flavor 的 PhoenixUI Android App 提供会员制激活服务。与现有激活制 flavor（mjguoguan1、tcb1 等）不同，mjarch 采用类似会员订阅的机制，支持有效期、单设备登录和激活码顺延。

> **重要约束**：本文档描述的新激活机制**仅用于 mjarch flavor**。其他所有 flavor（mjguoguan1、tcb1、jdgamespace 等）保持原有旧激活机制（ActivationAccessControl + 旧 PHP 后端）不变，不在本文档范围内，也不允许受到本次改动影响。

## 主流程（用户视角完整链路）

> 2026-10-02 补充确认，作为 mjarch App 端实现的权威场景描述。

1. **启动与列表加载**
   - 用户下载 App 后首次进入，App 自动从服务端拉取游戏配置列表，存一份到本地
   - 将服务端配置按 `rom_name` 在内存中覆盖到本地 gamelist 对象的对应属性（`required_levels` 等）
   - 游戏列表页按 **免费区 / VIP区** 两个分区展示游戏

2. **点免费区游戏**
   - 不需要登录，直接进入游戏

3. **点 VIP区游戏**
   - 弹出选择框：**会员购买** 或 **激活码激活**

4. **选择「激活码激活」**
   - **未登录**：弹出邮箱 + 密码 + 激活码输入框，一步完成用户创建 + 会员激活（oneStepActivate）
   - **已登录**：只弹出激活码填写确认（activate）

5. **选择「VIP会员购买」**（2026-10-03 修订）
   - **未登录**：先弹出**注册界面**（非登录界面，含「已有账号？去登录」切换入口）；注册完成后**自动登录，不再弹出登录界面**，直接进入套餐购买页
   - **已登录**：直接进入套餐购买页，选择套餐后微信 H5 支付
   - 支付成功后自动激活对应会员等级

## 业务场景

### 场景 1：免费体验
用户下载 App 后可以直接玩免费游戏，无需登录注册，降低使用门槛。

### 场景 2：淘宝购买激活码
用户在淘宝购买后，激活码 = 淘宝订单号。用户打开 App 输入邮箱+密码+淘宝订单号，一步完成注册/登录+激活。

### 场景 3：App 内购买
用户在 App 内查看套餐价格，登录后通过微信支付购买，支付成功后自动激活。

## 游戏分类

| 类型 | 访问权限 | 说明 |
|------|----------|------|
| 免费游戏 | 无需登录 | 引流，让用户先体验 |
| 会员游戏 | 需要对应等级会员 | 付费内容，不同游戏可要求不同会员等级 |

## 会员等级模型

- 用户的会员等级是一个**集合**，可以同时拥有多个等级标签
- 各等级相互独立，没有高低之分，是不同的权益身份
- 每个等级各自有独立的有效期
- 使用 `MembershipLevel.Code` 标识等级（如 "normal", "vip", "premium"）

**示例**：
- 用户有 `[{level_code: "normal", expires_at: 12/31}, {level_code: "vip", expires_at: 11/30}]`
- 游戏 A 配置 `required_levels = ["normal", "vip"]`，用户有 normal 或 vip 未过期，都可以玩

## 游戏列表数据来源

采用**混合模式**：

1. **客户端本地数据**：APK 打包的 `files.zip` 中的 `gamelist` 文件作为基础数据
2. **服务端覆盖数据**：服务端返回有配置的游戏列表，格式为 `{ "rom_name": "xxx", "required_levels": ["normal", "vip"] }`
3. **客户端叠加逻辑**：
   - 另外存储服务端返回的数据（SharedPreferences 或本地文件）
   - 呈现前按 `rom_name` 匹配，用服务端数据覆盖本地数据的对应字段
   - 本地没有的游戏不显示（服务端数据只用于补充属性，不新增游戏）
   - 不存在于服务端 games 表的游戏默认为免费

4. **刷新时机**：
   - App 启动时同步一次
   - 之后每 6 小时自动同步一次（后台定时）

## 用户故事

### US-01: 用户注册
**As a** 新用户
**I want to** 使用邮箱和密码注册账号
**So that** 我可以创建会员身份并开始使用服务

### US-02: 用户登录
**As a** 已注册用户
**I want to** 使用邮箱和密码登录
**So that** 我可以在设备上恢复我的会员身份

### US-03: 免费游戏体验
**As a** 新用户
**I want to** 无需登录直接玩免费游戏
**So that** 我可以先体验再决定是否购买会员

### US-04: 激活会员（淘宝用户）
**As a** 淘宝购买了激活码的用户
**I want to** 输入邮箱+密码+淘宝订单号一步完成注册和激活
**So that** 我可以快速开始使用会员功能

### US-05: 购买会员（App 内购）
**As a** 用户
**I want to** 在 App 内查看套餐并购买
**So that** 我可以通过微信支付开通会员

### US-06: 单设备登录
**As a** 已登录用户
**I want to** 在一台设备上使用我的账号
**So that** 我的会员权益得到保护

### US-07: 会员到期顺延
**As a** 会员用户
**I want to** 使用新的激活码时从当前剩余时间基础上顺延
**So that** 我不会损失已购买的会员时间

### US-08: 激活码恢复
**As a** 会员用户
**I want to** 在会员过期后使用之前的激活码恢复会员身份
**So that** 我可以在需要时重新激活

## 功能需求

### FR-01: 用户管理
- FR-01.1: 支持邮箱+密码注册
  - 邮箱查重，已存在则提示"该邮箱已注册，请更换邮箱或直接登录"
  - 密码长度 ≥ 6 位，不做复杂度要求
  - 密码不可为空
- FR-01.1a: **邮箱后缀自动补全**（2026-10-02 新增）
  - 适用界面：登录、注册、一步激活（激活码+邮箱+密码）所有邮箱输入框
  - 用户输入邮箱前缀时，自动下拉展示 `前缀@主流后缀` 候选列表，点击即完成输入，无需手动输入后缀
  - 候选后缀覆盖主流邮箱服务商，包括但不限于：
    - 国内：@qq.com、@163.com、@126.com、@foxmail.com、@sina.com、@sohu.com、@aliyun.com、@yeah.net、@139.com（移动）、@189.cn（电信）
    - 国际：@gmail.com、@outlook.com、@hotmail.com、@icloud.com、@yahoo.com
  - 已输入完整邮箱（含@）时不再追加候选
- FR-01.2: 支持邮箱+密码登录
- FR-01.2a: **登录框历史账号预填**（2026-10-03 新增）
  - 进入登录页时，若本地有历史登录账号则默认填入邮箱框，用户只需输密码（密码有默认值 888888）
  - 预填优先级：当前登录态邮箱（user_email）→ 最近登录邮箱（last_email，clearSession 时转存保留，FR-25 兜底字段复用）
  - 覆盖所有登录入口：购买未登录跳转、我的Tab登录、注册失败跳回、「登录已过期」弹窗重登（弹窗路径另有 relogin_email extra 传入，优先级最高）
  - 全新设备（从未登录过）两字段均为空，不预填
- FR-01.3: 忘记密码：联系客服处理（不提供自助重置）
- FR-01.4: 支持退出登录（调用 API 显式登出）
- FR-01.5: 密码存储使用 bcrypt 加密
- FR-01.6: **登录体系独立**：mjarch 只用邮箱登录，phone 字段为空；其他 flavor 用手机号+验证码登录，两套体系完全独立
- FR-01.7: **数据兼容**：biz_user 表 email/password 字段允许 NULL（兼容现有手机号用户），注册接口强制必填

### FR-02: 单设备登录
- FR-02.1: 用户同一账号同一时间只能在一台设备上登录
- FR-02.2: 登录时服务端记录设备登录状态（Redis）
- FR-02.3: 未登出时，再次在另一设备登录要提示"需要先登出原设备"
- FR-02.4: 原设备无法使用时，提示"联系客服处理"（客服可后台强制登出）
- FR-02.5: 登出时调用 API 显式登出，服务端清除登录状态

### FR-03: 游戏访问控制
- FR-03.0: 游戏列表页按 **免费区 / VIP区** 两个分区展示（分区依据：required_levels 是否为空）
- FR-03.1: 游戏列表采用混合模式：客户端本地 gamelist + 服务端覆盖数据
  - 服务端只返回有配置的游戏（`rom_name` + `required_levels`）
  - 客户端按 `rom_name` 匹配覆盖
  - 不存在于服务端的游戏默认为免费
- FR-03.2: 每个游戏配置 `required_levels`（会员等级 code 数组）
  - 空数组或不存在 = 免费游戏
  - `["normal"]` = 需要 normal 等级
  - `["normal", "vip"]` = normal 或 vip 任一满足即可
- FR-03.3: 游戏访问控制：检查用户是否拥有 required_levels 中任一等级，且该等级未过期
  - **必须按游戏逐个检查**（传入 gameConfig/romName），不允许降级为"有任意会员即放行"
- FR-03.4: 点击会员游戏时，未登录或等级不足则弹出引导（激活码激活 / 购买会员）
  - 已登录但等级不足：同样弹出引导（激活码补充激活 / 购买升级）
- FR-03.5: **刷新策略**：App 启动时同步一次，之后每 6 小时自动同步一次

### FR-04: 激活码管理
- FR-04.1: 激活码包含激活时长（天）和会员等级（level_code）
- FR-04.2: 激活码支持多次激活（`max_activations` 字段），每次激活 `used_activations += 1`
- FR-04.3: 激活码可以被不同用户使用，激活记录中记录是哪个用户激活的
- FR-04.4: 激活码激活后记录使用时间和使用者
- FR-04.5: 激活码支持自身过期时间（可选）
- FR-04.6: 支持创建激活码（管理端操作），指定会员等级和激活时长
- FR-04.7: 激活码有类型定义（模板），不同类型的激活码可以有不同的逻辑和默认属性
- FR-04.8: 激活码实例可以覆盖类型定义中的某些属性（会员等级、激活时长），默认继承类型定义
- FR-04.9: 激活码实例（activation_codes）和激活记录（activation_records）分开刻画
- FR-04.10: 激活码状态：0=未使用、1=已用完、2=已恢复、3=已取消
  - 状态保持为 0，直到 `used_activations == max_activations` 才变为 1
  - 判断是否可激活：`status != 3（已取消） && used_activations < max_activations`
- FR-04.11: 已取消的激活码不能用于激活，激活时提示"激活码已取消"
- FR-04.12: **淘宝激活码**：
  - 激活码 = 淘宝订单号
  - 复用现有 taobao_order 推送逻辑
  - 激活码表增加 `source` 字段（manual/taobao/app_purchase）
  - 淘宝来源关联 `taobao_order_id`
  - `max_activations = 淘宝订单购买数量`
- FR-04.13: **并发控制**：激活码更新使用乐观锁（version 字段）

### FR-05: 一步激活（公开接口）
- FR-05.1: 支持未登录状态下传入邮箱+密码+激活码，一步完成注册/登录+激活
- FR-05.2: 邮箱不存在时自动注册（用传入的密码，密码不可为空）
- FR-05.3: 邮箱已存在时验证密码
- FR-05.4: 验证通过后执行激活逻辑
- FR-05.5: 返回 token + 会员状态
- FR-05.6: **并发安全**：邮箱唯一约束冲突时捕获并重试查询

### FR-06: 会员管理
- FR-06.1: 支持多种会员等级（由 membership_levels 表配置，使用 code 标识）
- FR-06.2: 用户的会员等级是集合，可同时拥有多个等级，各自独立有效期
- FR-06.3: 会员有有效期，过期后自动失效
- FR-06.4: 同一用户同一等级使用新激活码时，从当前剩余时间基础上顺延
- FR-06.5: 支持激活码恢复（针对激活记录，非激活码）
  - FR-06.5.1: 只有原始激活用户才能恢复自己的激活记录
  - FR-06.5.2: 每个激活记录最多恢复3次
  - FR-06.5.3: 恢复时重新应用激活记录的会员等级和时长（顺延逻辑）
  - FR-06.5.4: App 端恢复为**自动触发，用户不可点击**（2026-10-02 修正）：
    - 触发时机 1：App 启动时（已登录状态）自动同步恢复
    - 触发时机 2：登录成功时自动恢复一次
  - FR-06.5.5: **恢复语义为覆盖而非叠加**（2026-10-02 修正）：恢复后 App 本地会员身份 = 服务端返回的会员身份，直接整体覆盖本地缓存
- FR-06.6: 用户可以查看自己的激活记录列表
  - **App 端入口**：「我的」Tab → 会员状态页（MembershipStatusActivity），展示会员等级集合 + 激活记录 + 登出
- FR-06.7: 支持取消激活码（管理端操作），取消后该激活码贡献的会员时间从用户总会员时间中减去

### FR-06.5x: 恢复的适用场景（2026-10-02 澄清，含同日修正）
- 恢复激活记录的真实用途：**用户登出后重新登录、或换手机登录时**，把服务端仍有效的激活记录重新应用到当前设备
- App 端不做手动恢复入口，全部自动：启动时（已登录）+ 登录成功时
- 恢复结果 = 服务端会员身份整体覆盖本地缓存（非叠加）

### FR-06.8: 会员身份定时检查（2026-10-02 新增）
- App 运行期每 6 小时定时查询一次服务端会员身份（/status），感知后台延期、取消等变化
- 同步成功后记录时间戳，6 小时内不重复请求（节流）
- 仅已登录时发起；未登录轮询空转
- 登录成功时 login 接口直接返回 memberships 并保存（换机/重登场景的会员身份带下来）

### FR-06.9: 管理端会员身份列表（2026-10-02 新增）
- **现状问题**：`dev-web-admin/src/views/license/Members.vue` 是占位空页（"会员管理功能开发中"），后端 admin 路由也没有会员身份查询接口
- **数据源**：`user_memberships` 表（user_id + level_code + expires_at），这是 C 端 /status、恢复逻辑的权威数据源（`buildMemberships()` 就是查这张表），管理端理应能看到
- **需求**：
  - 后端新增管理端接口：`GET /api/v1/admin/license/memberships`（分页列表）
  - 列表字段：用户ID、邮箱（关联 biz_user）、会员等级（level_code/level_name）、激活时间 activated_at、**过期时间 expires_at**、剩余天数、状态（有效/已过期）
  - 支持按邮箱/用户ID 搜索、按等级筛选、按状态（有效/过期）筛选
  - 与用户 1 对 N 关系展示（一个用户可有多个等级身份，每个身份一行）
  - （可选）管理端操作：手动调整过期时间、作废某个会员身份

### FR-18: 本地防时钟回拨的会员有效期判定（2026-10-03 新增）
- FR-18.1: 客户端持久化两个时间（SharedPreferences，`MODE_PRIVATE`，`allowBackup` 关闭或排除该文件）：
  - **启动时间**（last_boot_time）：App 每次启动时记录一次手机本地系统时间
  - **心跳时间**（heartbeat_time）：运行期每 30 秒记录一次本地系统时间，更新规则 = max(已记录值, 当前系统时间)，**单调不减**
- FR-18.2: 服务端联动：会员信息同步接口（/status 等）响应携带**服务器当前时间**（server_time）；自动恢复/同步会员状态时，仅当 server_time > 本地心跳时间才更新心跳时间（同样只增不减）。心跳时间因此始终是「本地或服务器见过的最大时间」
- FR-18.3: 会员有效期判定的参考时间 = max(心跳时间, 当前系统时间)，再与 expires_at 比较。用户将手机系统时间回拨到更早时，判定仍以心跳时间为下限，无法通过回拨延长会员
- FR-18.4: 防篡改：对两个时间值附加 HMAC 校验（密钥存 Android Keystore），读取时验签，校验失败视为被篡改，回退到保守处理（按已过期或重新从服务端同步）
- FR-18.5: 该机制仅影响客户端本地判定，服务端有效期判定不变（服务端时间本就可信）
- FR-18.6: 实现约束（2026-10-03 确认）：
  - 心跳定时器采用 **Handler.postDelayed 30 秒自循环**（前台运行期记录），不采用 WorkManager（其最小周期 15 分钟无法支撑 30 秒心跳）；App 被杀期间无心跳属预期行为，下次启动时启动时间与旧心跳时间按 max 原则自然衔接
  - SharedPreferences 写入必须用 `apply()`（异步落盘），禁止 `commit()`（同步落盘会阻塞主线程）
  - HMAC 密钥对象（Mac/SecretKey）进程内初始化一次缓存复用，不得每次心跳现取 Keystore（首次取密钥可达几十毫秒，后续签名本身微秒级）
  - 30 秒心跳开销预期：CPU 占用万分之几量级，游戏内无可感知影响
- FR-18.7: 到期时间下发增加 `expires_at_ms` 毫秒时间戳字段（2026-10-03 补充）：客户端判定优先取用毫秒时间戳（绝对时间，与服务端时区解耦），`expires_at` 墙钟字符串仅作旧版兼容回退——避免服务端机器非 +08:00 时区时客户端解析偏差 8 小时
