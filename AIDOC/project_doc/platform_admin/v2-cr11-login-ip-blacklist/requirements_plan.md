# 需求计划：登录失败 IP 黑名单（连续失败 N 次封禁 24 小时）

## 需求理解

**目标：** web admin 管理端登录场景下，同一 IP 连续登录失败达到阈值（系统配置项，默认 10 次）后，将该 IP 加入登录黑名单，后续 24 小时内该 IP 一律拒绝登录（即使账号密码正确）。

**范围：**
- 后端：登录链路（common/auth）增加失败计数与 IP 黑名单校验；黑名单存储 + 过期自动解封；阈值走系统配置（AdminConfig）
- 前端（dev-web-admin）：系统配置中新增该配置项的 seed/展示；黑名单列表查询 + 手动解封页面（供管理员处理误封）

**预期效果：**
- 攻击者从同一 IP 连续试错 10 次（可配置）后立即被封 24 小时
- 封禁期间该 IP 的所有登录请求直接拒绝并提示剩余封禁时间
- 管理员可查看黑名单列表并手动提前解封
- 24 小时到期自动解封，无需人工干预

## 假设列表

- [假设-1] 仅覆盖 web admin 管理端登录链路（common/auth 的 AuthHandler.Login），业务用户端登录（app/user_auth 的 biz_user 链路）本期不做
- [假设-2] 失败计数按 IP 维度统计（不区分用户名）：同一 IP 无论尝试哪个账号，失败累计；计数窗口滚动（如 30 分钟内累计），登录成功后该 IP 计数清零
- [假设-3] 阈值配置为平台级系统配置项（tenant_id=0），key 形如 `auth.login_fail_ban_threshold`（默认 10，0=关闭此功能）
- [假设-4] 黑名单需要持久化（服务重启不丢失），存 DB 表 + 进程内缓存加速校验；24 小时到期由查询时惰性判断过期，不依赖定时任务
- [假设-5] 封禁期间该 IP 所有登录请求（含密码正确的）一律拒绝，返回明确的"IP 已被封禁至 xx:xx"提示
- [假设-6] 黑名单页面需要新权限点（如 `system:loginblacklist`），默认授予平台管理员角色

## 澄清问题

- [Question-1] 失败计数的统计维度：按纯 IP 累计（假设-2），还是按 IP+用户名 组合累计（同一 IP 换账号试不累计）？
  业界做法：纯 IP 计数是主流（Nginx fail2ban、AWS WAF、各类后台框架如 go-admin/RuoYi 均按 IP），能防撞库+遍历账号；IP+用户名 维度对 NAT 出口（公司同一出口 IP 多人登录）更友好但防遍历能力弱。
  推荐：纯 IP 维度，配合 30 分钟滚动窗口 + 成功清零；误伤 NAT 场景由管理员手动解封兜底。
  [Answer-1]
IP+用户名 组合维度计数（同一 IP 对同一用户名连续失败累计）；封禁动作的目标仍是 IP（符合原始需求：失败达标后把该 IP 拉黑，封禁期间该 IP 全部登录拒绝）

- [Question-2] 黑名单存储位置：DB 新表（sys_login_blacklist）+ 内存缓存（推荐，重启不丢），还是纯内存缓存（重启即失效、简单）？多实例部署时 DB 方案天然共享。
  推荐：DB 新表 + 进程内缓存（TTL 60s），与现有 TokenBlacklist 的 store 抽象风格一致。
  [Answer-2]
DB 新表持久化 + Redis 缓存（走 sdk.Runtime.GetCacheAdapter()；Redis 不可用时降级进程内本地缓存，单实例模式）

- [Question-3] 封禁时长（24 小时）是否也做成配置项（如 `auth.login_fail_ban_hours`，默认 24），还是写死 24 小时？
  推荐：一并做成配置项，成本极低（同一读取链路），运维灵活。
  [Answer-3]
是。封禁时长做成配置项 auth.login_fail_ban_hours（默认 24），与阈值同一读取链路

- [Question-4] 被封 IP 尝试登录时，响应提示如何措辞？
  业界做法：明确提示"尝试次数过多，IP 已被临时封禁"并告知剩余时间，不暴露具体计数进度（避免帮攻击者试探阈值边缘）。
  推荐：提示"登录失败次数过多，该 IP 已被封禁，请 24 小时后重试或联系管理员"，返回剩余封禁分钟数（不返回累计失败次数）。
  [Answer-4]
同意推荐：不暴露累计失败次数，只提示已封禁+剩余时间

- [Question-5] 黑名单管理页面（查看+手动解封）是否本期必须，还是可以后补（先用 SQL 手工解封）？
  推荐：本期一起做——误封 NAT 出口后无法自助恢复会很难受；页面简单（列表+删除），成本低。
  [Answer-5]
同意：本期一起做黑名单管理页（列表+手动解封）

- [Question-6] 计数是否也持久化？即服务重启后失败计数是否清零（纯内存计数重启清零，攻击者可等待/触发服务重启来重置计数）。
  推荐：计数存内存即可（攻击者能触发服务重启的场景本身已是更高等级安全问题），黑名单必须持久化——这是安全边界所在。若要求严格，可把计数也落 DB（每次失败一次 UPDATE，量可控）。
  [Answer-6]
同意：失败计数走内存（重启清零可接受），黑名单必须 DB 持久化

## 非功能需求建议

- **性能：** 黑名单校验走内存缓存，登录接口额外耗时 < 1ms（P99）；缓存未命中回源 DB 单表主键查询
- **安全：** 黑名单增删接口需平台管理员权限；登录失败计数与封禁动作写 sys_login_log（复用现有登录日志，status=blocked）
- **多租户：** IP 黑名单为平台级全局数据（IP 不属于租户），不加 tenant_id 隔离；阈值配置为平台级（tenant_id=0）
- **兼容性：** 配置项缺省时（DB 无该 key）使用默认值 10，功能自动生效；配置为 0 时功能关闭，现有登录流程零影响

**新增：**
- `common/auth/model/login_blacklist.go` + repository + service（黑名单 CRUD + 校验 + 失败计数）
- `common/auth/handler/login_blacklist_handler.go`（列表+删除接口）
- migration：sys_login_blacklist 表 + 阈值/时长配置 seed
- 前端 `dev-web-admin/src/views/system/login-blacklist/` 页面 + 路由/权限 seed

**修改：**
- `common/auth/handler/auth_handler.go` — Login 入口加黑名单校验、失败后计数
- `common/auth/router.go` — 注册黑名单路由
- sys_login_log 写入侧补 blocked 状态

**不触碰：**
- 现有 TokenBlacklist（token 吊销）逻辑
- app/user_auth 业务用户登录链路（假设-1 成立时）
- 现有登录成功/失败响应格式（仅新增封禁分支的错误响应）
