# 需求计划：Platform Admin 架构设计 V2

## 需求理解

- 目标：基于现有 Platform Admin 架构 V1 的 review 发现，输出架构设计 V2 文档，解决已识别的 8 个架构问题，提升平台对多业务类型、多应用形态的灵活扩展、集成和维护能力
- 范围：本 CR 仅产出设计文档（design_v2.md），不涉及代码实现
- 预期效果：生成一份完整的架构设计 V2 文档，覆盖以下改进方向：
  1. 插件系统与 RBAC 权限体系统一
  2. 数据权限模型增强（scope_type 规则表达式）
  3. 租户配置能力增强（三级配置链）
  4. 缓存与权限中间件性能优化
  5. 应用模型类型区分（BUILTIN/PLUGIN/EXTERNAL）
  6. 角色继承策略明确化
  7. 插件间通信契约
  8. 前端插件 SDK 生命周期管理

## 澄清问题

- [Question-1] 角色继承策略：V2 中是否采用「权限继承」（子角色自动拥有父角色全部权限）？还是保持「仅分组展示」不参与权限计算？
  [Answer-1]
这里不是自动继承胡角色全部，应该是，影响这个角色可配置的的权限的范围，范围只能是互角色的子集，可以等于，不能大于父角色的权限范围，请读后给出你的理解
- [Question-2] 租户级配置：是否需要支持「租户级功能开关」（如某租户关闭某个应用模块）？还是仅支持参数级配置覆盖？
  [Answer-2]
需要支持，但需要把设计描述清楚
- [Question-3] 外部集成应用（EXTERNAL 类型）：当前是否有具体的集成场景（如 OAuth2 第三方登录、外部 API Gateway 对接）需要在 V2 中详细设计？还是仅预留扩展点？
  [Answer-3]
按业界最佳实践预留扩展点，需要在设计中描述清楚
- [Question-4] 插件权限同步到 RBAC 体系后，插件的权限是否需要支持「租户级订阅控制」（即不同租户可选择性启用插件的不同功能子集）？
  [Answer-4]
需要支持，需要在设计中描述清楚具体设计和逻辑
- [Question-5] V2 设计文档的详细程度：是否需要包含完整的 DDL 变更（ALTER TABLE 语句）和接口变更对照表？还是以方案设计为主、实施细节留给后续实现 CR？
  [Answer-5]
需要
## 非功能需求建议

- 向后兼容：V2 设计在有更优雅设计且确实性价比可以的情况下可以打破原先的设计，不用管数据迁移的问题，因为目前还未上生产

- 性能：权限检查链路 P99 < 5ms（缓存命中时）
- 扩展性：新增业务应用/插件时无需修改平台核心代码

## 影响范围预判

- 涉及模块：auth（权限/认证）、plugin（插件系统）、application（应用管理）、data-scope（数据权限）、cache（缓存）、frontend plugin-sdk
- 产出文件：`AIDOC/project_doc/platform_admin/domain_shared/design_v2.md`
- 不涉及代码变更
