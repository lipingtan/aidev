### 架构设计方法论

基于实际项目经验，形成了一套企业智能体系统的分层架构设计方法：

```
Layer 1: 用户/客户端层 — 多端接入（Web/移动/企微/钉钉/API/SDK）
Layer 2: API网关层 — 身份认证、路由、限流、会话管理
Layer 3: 编排控制层 — 工作流引擎、任务分解、计划与执行管理、上下文管理、守护策略
Layer 4: 专业化智能体层 — 调度/研究/推理/行动/数据/沟通智能体
Layer 5: 工具与知识层 — 网络搜索、API调用、代码执行、数据库、文件系统、知识库
Layer 6: 记忆与知识层 — 长期记忆、会话记忆、知识图谱、工作流模板、用户偏好
Layer 7: 监控与可观测性 — 追踪链路、日志、指标、告警、审计
Layer 8: 可靠性与故障管理 — 幻觉检测、重试回退、故障转移、人工介入、熔断器
Layer 9: 基础设施层 — LLM提供商、向量数据库、数据存储、消息队列、缓存、CI/CD
Layer 10: 业务本体（Ontology） — 实体/属性/关系、逻辑(Logic)、行动(Action)、权限(DAC)
Layer 11: 治理与安全 — 身份认证与授权、数据隐私、策略执行、模型提示词守护、合规审计
```

### 核心设计原则

1. **LLM 只输出意图，不直接执行** — 编排层做校验和执行，保证安全可控
2. **业务本体是 AI 的"眼睛"** — 没有 Ontology 语义层，LLM 无法理解业务
3. **约束校验是安全防火墙** — 防止 AI 幻觉造成业务损失
4. **渐进式自动化** — 建议→审批→自动，逐步建立业务信任
5. **可审计可回滚** — 每个决策有完整 input→reasoning→action 日志
6. **LLM 可替换** — Agent 编排层与 LLM 推理层解耦，支持多模型切换

## 附二：面试准备 — 核心问题与案例

### 1. Palantir 本体论（Ontology）的核心启发

**问题：你的 Ontology 设计思路来源是什么？**

Palantir 的核心竞争力不是某个算法，而是"本体论"驱动的体系能力：
- 把企业里的人、机器、订单、仓库等抽象为"对象"，定义关系，形成企业的"业务地图"
- 让 AI 能理解业务语境，而不只是处理数据字段
- 产品不是设计出来的，是工程师驻场客户现场"战地经验"堆出来的复利

**与 DDD 的区别：**
- DDD 是设计时规范，指导代码组织
- Ontology 是运行时语义层，数据本身带着业务含义存在于平台中
- DDD 的 Bounded Context 是隔离的；Ontology 的核心价值是打破数据孤岛，统一语义
- Ontology 给 AI 提供"业务上下文"——LLM 调用工具时知道"这个对象是什么、和谁有关系、能做什么操作"

### 2. Ontology 怎么给 AI 提供业务上下文（具体落地）

**没有 Ontology 时，AI 看到的是：**
```
table: inventory → warehouse_id=W001, sku_id=P123, qty=5
```
AI 不知道 W001 是哪里、P123 是什么、该找谁补货。

**有 Ontology 时，AI 看到的是：**
```
Object: 仓库[W001-上海浦东仓]
  属性: 地址、容量、负责人
  关系: 管理产品→[P123-SBS卷材, qty=5, 告警阈值=50] ← 低库存
       可调入来源→[W002-苏州仓, 距离80km, 库存=800]

Action（可执行操作）:
  - 发起调拨申请(from, to, sku, qty) → 写入 WMS
  - 触发采购(sku, qty) → 写入 ERP
```

技术链路：`用户问题 → LLM 解析意图 → 查 Ontology 图谱 → LLM 基于上下文推理 → 输出 tool_calls → 校验 → 执行写回`

---

### 3. Agent 是什么（面试必答）

**Agent = 你自己写的一段程序代码，不是框架也不是产品。**

本质是一个循环调度器：
```
while 任务未完成:
    1. 从 Ontology 获取当前业务状态
    2. 把状态喂给 LLM，问"下一步干什么"
    3. LLM 返回 tool_calls（结构化意图）
    4. 你的代码校验意图是否合理
    5. 合理就执行写回业务系统
    6. 把执行结果告诉 LLM，继续循环
```

LLM 是"大脑"，Agent 代码是"身体"。LLM 本身无权限直接写任何系统。

### 4. 架构解耦解决多步骤任务的状态管理和逻辑中断（具体案例）

**场景：防水建材产销协同决策**

完整流程：查库存 → 查订单 → 查产能 → 推理排产方案 → 校验约束 → 执行写回 → 确认结果

**不解耦的三个问题：**
1. 上下文溢出：13类对象×多仓库数据一次性塞入 Prompt，超 Token 限制或注意力分散
2. 中间步骤失败无法恢复：3个 Action 执行到第3个时 MES 超时，前2个已执行无法回滚
3. 人工审批阻塞：产能超限需主管审批，等几小时期间 Agent 不能一直占资源

**解耦方案：**

把流程拆成独立阶段，每步之间通过持久化状态衔接：

```
┌─────────────┐     ┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│ Step 1      │     │ Step 2      │     │ Step 3      │     │ Step 4      │
│ 数据采集    │────→│ 决策推理    │────→│ 约束校验    │────→│ 执行写回    │
│（确定性代码）│     │（LLM 调用） │     │（确定性代码）│     │（确定性代码）│
└──────┬──────┘     └──────┬──────┘     └──────┬──────┘     └──────┬──────┘
       ↓                   ↓                   ↓                   ↓
   [状态持久化]        [状态持久化]        [状态持久化]        [状态持久化]
```

**中断恢复逻辑：**
```python
def resume_planning(task_id: str):
    state = load_state(task_id)
    
    if state.status == "failed" and state.step == 4:
        # 第4步写回失败，只重试失败的 Action
        retry_failed_actions(state)
    
    elif state.status == "awaiting_approval":
        # 审批通过后从断点继续，不重新推理
        execute_approved_actions(state)
    
    elif state.status == "reasoning_timeout":
        # LLM 超时，用已有快照重新调用（不重新采集数据）
        actions = call_llm(state.snapshot)
        proceed_to_validation(state, actions)
```

**对比效果：**

| 情况 | 不解耦 | 解耦后 |
|------|--------|--------|
| MES 接口超时 | 整个流程重来 | 只重试失败的那一个 Action |
| 需要人工审批 | Agent 阻塞或放弃 | 挂起状态，审批后从断点继续 |
| LLM 幻觉 | 可能已写入业务系统 | 校验层拦截，不执行 |
| 审计追溯 | 只有最终结果 | 每步有快照，可回放 |

**面试话术：**
> "核心设计是：确定性逻辑（数据查询、校验、写回）用代码实现，只有'决策推理'这一步调用 LLM。LLM 的不确定性被限制在一个可控范围内，任何一步中断都能从断点恢复。"

### 5. 框架选型观点（Dify / LangGraph / LangChain）

| 场景 | 推荐 |
|------|------|
| 快速 POC / 内部知识问答 | Dify |
| 单一流程 RAG + 工具调用 | LangChain |
| 多步骤决策 + 审批 + 状态持久化 | LangGraph |
| 需要极致控制 + 企业级安全治理 | 纯代码 Agent |

**关键观点：** 无论选哪个框架，Ontology 层、约束校验、业务系统对接都得自己写，这部分占项目 70% 以上工作量。框架只解决"LLM 怎么调用、工作流怎么编排"，不解决"业务怎么建模、决策怎么校验"。

### 8. 框架选型案例：为什么选 LangGraph 而不是 Dify 或纯 LangChain

**背景：** 产销协同 Agent 技术选型，三种方案都做了尝试。

#### Dify 的尝试与放弃

POC 阶段用 Dify 搭了"库存问答 + 简单补货建议"Demo，2天上线，业务方满意。但进入生产需求后发现三个硬伤：

1. **不支持循环推理**：产销决策需要"LLM 生成方案 → 校验不通过 → LLM 重新调整"的循环，Dify 工作流是 DAG（无环图），不支持回退
2. **审批中断后无法恢复**：工作流同步执行到底，没有"挂起等审批，审批后从断点继续"的能力
3. **Action 写回太受限**：对接 MES/WMS 需要重试、补偿、幂等，Dify 的 HTTP 节点只能做简单调用

**结论：Dify 留给业务人员做知识问答和报表解读，核心决策 Agent 不用它。**

#### 纯 LangChain 的尝试与放弃

第一版用 `AgentExecutor` + 自定义 Tool：

```python
tools = [query_inventory_tool, create_order_tool, transfer_tool]
agent = create_tool_calling_agent(llm, tools, prompt)
executor = AgentExecutor(agent=agent, tools=tools)
result = executor.invoke({"input": "生成今日排产计划"})
```

跑通了基本流程，但遇到：
1. **状态丢失**：AgentExecutor 无状态，Tool 超时后整个流程重来
2. **无法插入审批节点**：Agent 循环是 LLM→Tool→LLM→结束，没有"暂停等人工"的机制
3. **多步骤编排靠 if-else 堆砌**：写到后面发现自己在重新发明 LangGraph

#### LangGraph 的最终实现

用状态图建模：

```python
from langgraph.graph import StateGraph
from langgraph.checkpoint.postgres import PostgresSaver

graph = StateGraph(PlanningState)
graph.add_node("collect_data", collect_business_data)
graph.add_node("reason", call_llm_for_decision)
graph.add_node("validate", check_constraints)
graph.add_node("wait_human", interrupt_for_approval)
graph.add_node("execute", write_back_to_systems)

# 条件分支：校验不通过回到 LLM 重新推理（循环）
graph.add_conditional_edges("validate", {
    "approved": "execute",
    "rejected": "reason",           # 循环
    "needs_approval": "wait_human"  # 中断挂起
})

# 状态持久化 → 断点恢复的关键
checkpointer = PostgresSaver(conn_string="postgresql://...")
app = graph.compile(checkpointer=checkpointer)
```

三个关键能力：
- **循环**：校验不通过时 validate→reason 形成循环，LLM 基于拒绝原因重新生成方案
- **中断恢复**：审批节点把状态写入 PG，流程挂起；审批通过后从断点继续，不重跑
- **故障重试**：execute 节点某个 MES 调用失败，重启后只重试失败部分

#### 最终三者分工

| 工具 | 负责场景 | 原因 |
|------|----------|------|
| Dify | 业务人员自助应用（知识问答、报表解读） | 上手快，非技术人员可维护 |
| LangGraph | 核心决策 Agent（产销协同、排产、调拨） | 循环/中断/持久化原生支持 |
| LangChain 组件 | Tool 抽象、Retriever 复用 | 生态丰富，不重复造轮子 |
| 自研代码 | Ontology 层、约束校验、Action 写回、审计 | 框架不提供，必须自己写 |

#### 面试话术

> "项目里三种工具都用了。Dify 做面向业务人员的简单应用，2天上线；核心决策 Agent 用 LangGraph，因为它原生支持循环推理、人工审批中断、状态持久化；LangChain 的 Tool 和 Retriever 作为底层组件复用。但最关键的 Ontology 层、约束校验、业务系统写回是自研的——框架解决编排问题，业务逻辑必须自己写。"
