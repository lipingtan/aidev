# 技能：多角色设计 Review

## 触发条件

当用户消息包含以下词语时激活本技能：
「多角色review」「三角色review」「设计review」「review一下」「需求review」「架构review」「architecture review」「帮我review」「审查一下」

---

## 角色

三位评审专家各有侧重，**不重复审查相同维度**：

| 角色 | 核心视角 | 不负责 |
|------|---------|--------|
| 业务专家 | 业务完整性、租户隔离、跨行业适用性 | 技术实现细节 |
| 产品经理 | 用户体验、验收标准可测性、前后端对齐 | 数据库/代码层面 |
| 架构师 | 数据模型、API 规范、性能/安全/并发 | 业务场景合理性 |

---

## 输入文档

按以下顺序查找并读取（有则读，不存在则跳过）：
1. 当前打开的编辑器文件
2. `requirements.md` — 用户故事 / FR-N 验收标准
3. `design.md` — 数据模型 / API 设计 / 状态机 / 不变行为清单
4. `tasks.md` — 任务拆解 / Scope / Acceptance

**任何文件不存在时**：在 review 开始前说明"以下文档未找到，对应角色的部分检查项将跳过：{文件列表}"，然后继续。

---

## 严重度定义

所有角色统一使用以下严重度等级：

| 等级 | 含义 |
|------|------|
| 高 | 核心功能缺失 / 数据错误 / 安全问题 / 发布阻断 |
| 中 | 功能降级 / 边界遗漏 / 影响部分用户 |
| 低 | 体验问题 / 文案描述 / 非关键路径 |

---

## 工作流程

### 执行顺序

三个角色**依次完成各自 review**，汇总全部问题后，**一次性**请用户确认修复，再批量执行修复。

```
角色1 review → 角色2 review → 角色3 review
                                    ↓
                        汇总问题清单（去重合并）
                                    ↓
                        请用户确认修复哪些问题
                                    ↓
                             批量修复 → 完成
```

**不在每个角色结束后单独中断等待确认。**

---

## 角色 1：资深多租户跨行业业务专家

**侧重**：业务场景完整性、多租户隔离规则、跨行业 SaaS 适用性。

检查维度：

**业务完整性**
- 核心业务流程是否完整？关键业务场景是否有遗漏？
- 所有业务角色（平台管理员 / 租户管理员 / 普通用户 / C端用户）的操作路径是否覆盖？
- 异常场景（租户到期/配额超限/应用停止/数据迁移）是否有对应处理？

**多租户隔离**
- 租户间数据、权限、配置是否正确隔离？
- 跨租户操作（如平台管理员查所有租户）是否明确标注权限边界？

**跨行业适用性**
- 功能设计是否具有通用性，避免行业强依赖？
- 术语和概念是否在全文档中统一、无歧义？

**不检查**：API 命名、DDL 字段、代码实现。

输出格式：

| # | 严重度 | 问题描述 | 建议方案 |
|---|--------|---------|---------|
| B-1 | 高/中/低 | ... | ... |

无问题时输出：`✅ 角色1（业务专家）未发现问题`

---

## 角色 2：资深产品经理

**侧重**：用户体验、验收标准可测性、前后端字段对齐。

检查维度：

**用户体验**
- 用户故事是否反映真实需求？交互流程是否符合用户心智模型？
- 前端用户感知是否合理（菜单可见性 / 权限提示 / 状态展示 / 错误提示）？

**验收标准可测性**
- 每条验收标准是否**可测试**（有明确的输入、操作、可观测结果）？
- 是否存在"应该""可能""尽量"等模糊描述？如有，必须改为确定性表述。

**前后端对齐**
- 需求中的验收标准与 design.md 中的 API/业务逻辑是否对齐？
- 前后端接口字段名/类型/结构是否一致（特别是 int64 的 string 序列化、枚举值定义）？
- 管理端和用户端的功能对称性是否合理？

**不检查**：数据库索引、代码并发安全、技术架构选型。

输出格式：

| # | 严重度 | 问题描述 | 建议方案 |
|---|--------|---------|---------|
| P-1 | 高/中/低 | ... | ... |

无问题时输出：`✅ 角色2（产品经理）未发现问题`

---

## 角色 3：资深架构师

**侧重**：数据模型、API 设计规范、性能/并发/安全边界。

检查维度：

**数据模型**
- DDL 字段/类型/索引/约束是否正确？
- GORM Model 的 tag 与 DDL 是否一致？
- 是否有缺失的唯一约束、外键或软删除字段？

**API 设计**
- API 是否 RESTful（HTTP 方法、URL 语义、状态码映射）？
- 请求/响应字段命名是否符合项目规范？
- 分页、过滤、排序参数是否统一？

**中间件与依赖**
- 中间件链路顺序是否正确（认证 → 解析应用 → 权限检查 → 字段过滤）？
- 是否有遗漏或多余的中间件？

**边界与安全**
- 并发写入是否有乐观锁/事务保护？
- 递归/级联操作是否有深度限制和循环引用检测？
- 敏感字段是否做了脱敏/隐藏处理？
- 输入校验是否覆盖空值/超长/非法枚举？

**不变行为清单（回归防护）**
- design.md 中的 RG-N 不变行为是否完整覆盖所有改动的影响面？
- 任务拆解的 Acceptance 标准是否包含回归验证点？

**不检查**：用户故事合理性、业务场景完整性、产品交互逻辑。

输出格式：

| # | 严重度 | 问题描述 | 建议方案 |
|---|--------|---------|---------|
| A-1 | 高/中/低 | ... | ... |

无问题时输出：`✅ 角色3（架构师）未发现问题`

## 汇总与修复

### 汇总问题清单

三个角色 review 完成后，合并输出汇总表（去掉重复问题，按严重度排序）：

```
## 汇总问题清单

| # | 来源 | 严重度 | 问题描述 | 建议方案 |
|---|------|--------|---------|---------|
| 1 | 架构师 | 高 | ... | ... |
| 2 | 产品经理 | 中 | ... | ... |
| 3 | 业务专家 | 低 | ... | ... |

共 {N} 个问题（高: N / 中: N / 低: N）

是否全部修复？还是选择性修复（请告知编号）？
```

### 修复执行

- 用户确认后，按清单顺序批量修复对应文档
- 修复完成后，对每条已修复的问题标注 `✅ 已修复`
- 无法修复（文档范围外）的问题标注 `⚠️ 待处理，建议记录到 todo.md`

### 全部通过

所有问题修复完毕后输出：

```
✅ 三角色 review 完成，全部问题已修复，文档可进入下一阶段。
```

## 典型 Review 关注点速查

| 场景 | 优先由哪个角色检查 |
|------|-----------------|
| 租户隔离规则 | 业务专家 |
| 验收标准模糊 | 产品经理 |
| int64 序列化问题 | 产品经理（字段对齐） |
| 乐观锁/事务 | 架构师 |
| 中间件顺序 | 架构师 |
| 业务角色覆盖 | 业务专家 |
| 枚举值定义 | 产品经理 + 架构师 |
| 递归深度限制 | 架构师 |
