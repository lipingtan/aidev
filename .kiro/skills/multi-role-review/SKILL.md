# 技能：多角色设计 Review

## 触发条件

当用户需要对 CR 的需求（requirements.md）、设计（design.md）、任务拆解（tasks.md）进行多角色审查时激活。触发词：「多角色review」「三角色review」「设计review」「review一下」。

## 工作流程

按以下顺序依次执行三个角色的 review。每个角色完成后：
- 无问题 → 直接进入下一个角色
- 有问题 → 列出问题清单 + 修正方案/建议 → 请求用户确认是否修复 → 修复后进入下一个角色

---

## 角色 1：资深多租户跨行业业务和领域专家

从业务视角检查以下维度：

**合理性**：
- 业务场景是否完整覆盖？是否遗漏关键业务流程？
- 多租户隔离是否合理？租户间数据/权限/配置是否正确隔离？
- 是否符合跨行业通用 SaaS 平台的最佳实践？

**一致性**：
- 需求、设计、任务之间的业务概念是否前后一致？
- 术语定义是否在文档间统一？

**完整性**：
- 所有业务角色（平台管理员/租户管理员/普通用户/C端用户）的操作路径是否覆盖？
- 异常场景（租户到期/配额超限/应用停止）是否考虑？

**清晰度**：
- 概念定义是否清晰无歧义？
- 业务规则是否可被开发人员准确理解和实现？

输出格式：

| # | 严重度 | 问题 | 建议方案 |
|---|--------|------|---------|

---

## 角色 2：资深产品经理

从产品视角检查以下维度：

**合理性**：
- 用户故事是否合理？是否反映真实用户需求？
- 交互流程是否符合用户心智模型？
- 前端用户感知是否合理（菜单可见性/权限提示/状态展示）？

**一致性**：
- 需求中的验收标准与设计中的 API/逻辑是否对齐？
- 前后端接口字段名/类型/结构是否一致？

**完整性**：
- 验收标准是否可测试、无遗漏？
- 是否覆盖异常操作的友好提示？
- 管理端和用户端的功能对称性是否合理？

**清晰度**：
- 产品行为描述是否明确到"什么条件下发生什么"？
- 是否有模糊的"应该"、"可能"等不确定描述？

输出格式同上。

---

## 角色 3：资深架构师

从技术架构视角检查以下维度：

**合理性**：
- 数据模型设计是否合理？DDL 字段/索引/约束是否正确？
- API 设计是否 RESTful、命名一致、方法正确？
- 中间件链路顺序是否正确？是否有遗漏或多余？
- 性能/缓存/并发是否有隐患？

**一致性**：
- DDL 中的字段与 Model 代码中的 GORM tag 是否一致？
- 设计文档中的伪代码与需求中的验收标准是否对齐？
- 不同章节对同一概念的描述是否一致？

**完整性**：
- 核心逻辑是否有边界遗漏（空值/并发/循环引用）？
- 不变行为清单是否覆盖所有回归风险？
- 任务拆解的 Scope/依赖/验收标准是否完整？

**清晰度**：
- 技术方案是否可被开发人员直接实现（无需再猜测）？
- 任务之间的依赖关系是否明确标注？

输出格式同上。

---

## 全部通过

当三个角色依次 review 完毕且所有问题已修复后，输出：

```
✅ 三角色 review 通过，文档可进入下一阶段。
```
