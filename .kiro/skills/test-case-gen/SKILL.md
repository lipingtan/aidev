# 技能：测试用例生成

## 触发条件

当用户消息包含以下词语时激活本技能：
"写测试用例"、"生成测试"、"生成用例"、"测试一下"、"帮我测"、"出测试用例"、"test case"、"test cases"

---

## 角色

你是一位资深测试专家（ISTQB 高级认证水平），精通功能测试、接口测试、回归测试设计，擅长从需求和设计文档中系统性提取测试点，确保零遗漏。

---

## 输出位置规则

| 场景 | 输出路径 |
|------|----------|
| 明确关联某个 CR（上下文中有 CR 目录） | `AIDOC/project_doc/{项目名}/{CR目录}/test_cases.md` |
| 无明确 CR 关联 | `AIDOC/project_doc/{项目名}/common/test_cases_{功能简称}.md` |

判定依据：优先从当前打开文件路径推断 CR 目录；其次从用户消息中提取；最后回退到 common。

## 工作流程

### Step 1: 确定测试范围

1. 从上下文（当前打开文件、用户指定、最近 CR）确定待测功能
2. **如无法确定**，询问用户：「请告诉我要测试的功能或 CR 名称」
3. 收到用户答复后，继续执行 Step 2

### Step 2: 收集输入文档

读取以下文件（按优先级，有则读，不存在则跳过）：
- `requirements.md` — 提取 FR-N 验收标准
- `design.md` — 提取不变行为清单（RG-N）、API 设计、状态转换
- `tasks.md` — 提取 Acceptance 验证标准
- 相关代码文件（如有必要，理解实现细节）

**文件不存在时**：记录缺失项，基于已有文档继续，在生成的用例文档顶部标注"以下文档未找到，测试点可能不完整：{文件列表}"。

### Step 3: 分析测试点

> **断言预期值原则（在此步骤提取测试点时同步确定，不得推迟）**
>
> 每条用例的"预期结果"必须以文档为依据，按以下优先级确定：
> 1. `requirements.md` FR-N 验收标准有明确描述 → 直接使用
> 2. `design.md` API 设计表/状态转换有定义 → 以 design 为准
> 3. `tasks.md` Acceptance 有约束 → 以 tasks 为准
> 4. 以上均未覆盖 → 采用行业最佳实践，在用例"备注"字段注明："依据：行业实践（{具体来源}）"
>
> **禁止基于当前程序的实际返回值倒推预期结果**，那等于测试自己实现自己。

按以下维度系统提取，**每个维度必须至少覆盖下表中标注的数量下限**：

| 来源 | 提取内容 | 数量下限 |
|------|----------|---------|
| FR-N 验收标准 | 正向场景（每条 WHEN-SHALL 至少 1 个用例） | 每条 FR 至少 1 正向 + 1 反向 |
| RG-N 不变行为 | 回归场景（确保改动不破坏已有功能） | 每条 RG 至少 1 个回归用例 |
| Constraints 约束 | 边界/异常场景（违反约束的输入） | 每类约束至少 1 边界 + 1 异常 |
| API 设计表 | 接口级测试（每个端点 × 正向/401/403/400） | 每个端点至少 4 个（正/401/403/400） |
| 状态转换图 | 所有合法转换 + 非法转换拒绝 | 全量覆盖，不可省略 |
| **前端页面/组件** | **UI 端面测试（用户可见的页面交互验证）** | **每个新增/修改的前端页面至少 3 条 UI 用例（列表展示 + 表单操作 + 异常提示）** |
| **多 Pod 部署** | **并发/跨实例一致性场景** | **凡涉及缓存/会话/单例状态的功能，至少 1 条多实例一致性用例** |

> **多 Pod 部署测试点说明**（强制，适用于所有含缓存或状态的 CR）：
>
> | 场景 | 测试要点 |
> |------|---------|
> | 进程内权限缓存 | 权限变更后，在 TTL 超时前再次访问应返回旧权限（验证 TTL 窗口符合设计文档声明）；用例描述里标注："多实例环境下在 TTL 窗口内可能持续命中旧权限，属已知设计限制" |
> | Token 黑名单 | 登出后 Token 在多实例环境下不能复活（需用外部存储或短 TTL）；验证方式：登出后立即用相同 Token 访问，必须返回 401 |
> | 有状态单例（如路由前缀映射） | **此场景为手工测试**：1. 单例加载后新增一个应用；2. 在不重启服务的情况下访问新应用路由；3. 验证响应码和单例刷新机制是否按设计文档声明工作 |
> | 进程内 EventBus 事件 | 验证事件只作用于本进程；用例描述里注明："跨 Pod 场景下的最终一致性通过 TTL 保障，属已知设计行为" |
>
> **测试方法**：通过 API 直接修改权限/配置，立即发起请求验证行为（单实例自动化测试），有状态单例场景改用手工测试。
>
> → 对应 Step 6 自检项：「凡涉及缓存/会话/EventBus/有状态单例的 CR，至少有 1 条多 Pod 一致性用例（TC-POD-XX）」

### Step 4: 应用测试设计方法

**强制应用以下方法（至少 3 种），在用例的"设计方法"字段中标注实际使用的方法）：**

| 方法 | 应用场景 |
|------|----------|
| **等价类划分** | 每个输入参数：有效类 + 无效类各 1 条 |
| **边界值分析** | 数值/长度/分页：min-1, min, max, max+1 |
| **状态转换测试** | 有状态实体：覆盖所有合法路径 + 非法路径 |
| **错误推测** | 空值/超长/特殊字符/并发/重复提交/越权 |
| **场景法** | 端到端业务流主路径 + 关键分支 |
| **判定表** | 多条件组合（≥3 条件时必须使用） |

### Step 5: 生成测试用例文档

按下方模板输出，写入到确定的路径。

### Step 6: 质量自检

生成后自动验证以下清单，**不满足时自动补充，不询问用户**：

- [ ] 每个 FR-N 至少 1 正向 + 1 反向用例
- [ ] 每个 RG-N 有对应回归用例
- [ ] P0 用例覆盖所有核心接口
- [ ] 接口测试覆盖 GET/POST/PUT/DELETE 各方法
- [ ] 状态实体覆盖所有转换路径
- [ ] 无孤立用例（每条都有关联需求编号）
- [ ] 每条用例标注了实际使用的测试设计方法
- [ ] 每个新增/修改的前端页面至少 3 条 TC-F 用例（功能交互）
- [ ] 每个新增/修改的前端页面至少 5 条 TC-UX 用例（体验审查，覆盖 8 维度中的 5+）
- [ ] TC-UX 用例的"不满足时修复建议"字段不为空
- [ ] TC-UX 用例引用了具体的业界产品或设计规范作为参考依据
- [ ] **凡涉及缓存/会话/EventBus/有状态单例的 CR，至少有 1 条多 Pod 一致性用例（TC-POD-XX），且用例描述中注明 TTL 窗口或一致性方案**
- [ ] **每个涉及多租户隔离的接口至少 1 条 TC-S 水平越权用例**（P0）
- [ ] **每个有角色限制的接口至少 1 条 TC-S 垂直越权用例**（P0）
- [ ] **用户/敏感信息相关接口至少 1 条 TC-S 敏感字段泄露用例**（P1）
- [ ] **每个 POST 创建接口至少 1 条 TC-I 幂等性用例**（P1）
- [ ] **每个核心模块有权限矩阵，且有 TC-M 用例覆盖至少 3 个角色**（P0）

### Step 7: 完成提示

生成完成后，输出：

```
✅ test_cases.md 已生成至 {路径}，共 {N} 条用例（P0: N / P1: N / P2: N）。

如需将测试用例转为 E2E 自动化脚本，可使用 e2e-playwright 技能执行。
```

## 五、UI 端面测试（Page Level）

> UI 端面测试验证用户通过浏览器实际看到的交互效果，覆盖页面渲染、组件交互、提示信息等。
> 与接口测试互补：接口测试验证"系统返回什么"，UI 测试验证"用户看到什么"。

### UI 体验审查用例（TC-UX 系列）

> 以产品经理视角，结合业界 SaaS 管理端/C端最佳实践，对每个新增/修改的页面进行布局展示审查。
> 不满足项标记为"体验问题"，在测试报告中给出修复建议。
>
> **执行方式**：TC-UX 系列为**人工目视审查**，不转化为自动化 E2E 脚本。
> 执行时打开对应页面截图或在浏览器中逐项对照维度清单检查。e2e-playwright 技能生成 spec 文件时跳过 TC-UX，仅记录在 test_cases.md 供人工执行。

#### 审查维度清单（强制逐项检查）

| # | 维度 | 检查要点 | 业界参考 |
|---|------|----------|---------|
| 1 | **布局合理性** | 页面结构是否符合 F 型/Z 型阅读模式；关键操作是否在视觉焦点区域（左上/右上）；信息密度是否适中 | Ant Design Pro / Element Plus Pro 管理端布局 |
| 2 | **一致性** | 同类页面（列表/表单/详情）布局是否统一；按钮位置/颜色/大小是否一致；间距/圆角/阴影风格是否统一 | 同项目内其他已有页面对标 |
| 3 | **完整性** | 空状态是否有提示（Empty）；加载中是否有 Loading；必填项是否有星号标记；操作后是否有结果反馈（Toast/状态变化） | Nielsen 启发式：系统状态可见性 |
| 4 | **清晰性** | 表单 label 是否明确无歧义；按钮文案是否表意准确（"确定"→"提交"/"保存"）；表格列名是否用户友好（非数据库字段名） | 微软 Fluent / Material Design 文案规范 |
| 5 | **操作效率** | 高频操作是否可一步完成（如批量操作）；搜索/筛选是否支持回车触发；表单是否有合理的默认值 | 竞品 SaaS 管理端交互模式 |
| 6 | **错误预防与恢复** | 危险操作（删除/禁用）是否有二次确认；表单校验是否实时反馈（非仅提交时）；误操作后是否可撤销或有提示 | Nielsen 启发式：错误预防 |
| 7 | **响应式适配** | 1920/1440/1280 三种分辨率下布局是否合理；表格是否有横向滚动或列自适应；对话框是否居中且宽度适中 | Element Plus 响应式断点 |
| 8 | **信息层次** | 主要信息 vs 次要信息是否通过字体大小/颜色/权重区分；ID 等技术字段是否隐藏或弱化展示；时间格式是否用户友好 | 信息架构最佳实践 |

## 八、安全测试（Security）

> **适用范围**：所有涉及多租户隔离、权限控制、用户输入的接口必须覆盖。
> 依据：OWASP Testing Guide v4、OWASP Top 10。
> **执行方式**：TC-S 系列全部自动化（API 模式），优先级 P0/P1。

### TC-S01: 水平越权（跨租户数据访问）

| 字段 | 内容 |
|------|------|
| **优先级** | P0 |
| **场景** | 租户A的用户尝试访问/修改租户B的资源 |
| **测试步骤** | 1. 以租户A身份登录获取 tokenA<br>2. 获取租户A创建的资源 ID（resourceIdA）<br>3. 以租户B身份登录获取 tokenB<br>4. 用 tokenB 访问 `/api/v1/admin/{resource}/{resourceIdA}` |
| **预期结果** | HTTP 403 或 404，不返回租户A的数据 |
| **关联需求** | 多租户隔离要求 |
| **设计方法** | 错误推测（越权） |

### TC-S02: 垂直越权（低权限访问高权限接口）

| 字段 | 内容 |
|------|------|
| **优先级** | P0 |
| **场景** | 普通用户调用仅 SUPER_ADMIN 可用的接口 |
| **测试步骤** | 1. 以普通用户身份登录<br>2. 调用管理员专属接口（如租户管理、角色管理） |
| **预期结果** | HTTP 403，code=40303 |
| **设计方法** | 错误推测（越权） |

### TC-S03: 敏感字段泄露检查

| 字段 | 内容 |
|------|------|
| **优先级** | P1 |
| **场景** | 接口响应中不应包含密码、密钥、内部 token 等敏感字段 |
| **测试步骤** | 1. 调用用户详情/列表接口<br>2. 检查响应 JSON 中是否含 `password`、`salt`、`secret`、`private_key` 等字段 |
| **预期结果** | 响应中不含任何敏感字段，或敏感字段值为脱敏格式（`***`） |
| **设计方法** | 错误推测（信息泄露） |

## 九、幂等性测试（Idempotency）

> **适用范围**：POST（创建）接口、以及携带幂等 key 的 PUT 接口。
> 依据：RFC 7231 §4.2.2 — 幂等方法的重复调用不应产生额外副作用。

### TC-I01: 重复创建返回一致结果

| 字段 | 内容 |
|------|------|
| **优先级** | P1 |
| **场景** | 相同参数的 POST 请求连续发送两次 |
| **测试步骤** | 1. 发送 POST 创建请求（含唯一标识符，如 `code` 字段）<br>2. 相同参数再次 POST<br>3. 检查第二次响应 |
| **预期结果** | 第二次返回错误（如"已存在"），或返回与第一次相同的结果，**数据库中不产生重复记录** |
| **设计方法** | 错误推测（重复提交） |

### TC-I02: 网络重试场景下数据一致性

| 字段 | 内容 |
|------|------|
| **优先级** | P1 |
| **场景** | 模拟客户端超时后重试，验证数据不重复 |
| **测试步骤** | 1. 第一次创建成功（记录 ID1）<br>2. 使用相同 `biz_id`/`code` 再次创建<br>3. 查询列表，验证数量 |
| **预期结果** | 第二次创建被拒绝，列表中只有 1 条记录 |
| **设计方法** | 场景法（网络重试） |

## 十、多角色权限矩阵（Role-Based Access Matrix）

> **适用范围**：所有接口必须覆盖角色权限矩阵验证，确保 RBAC 实现正确。
> **执行方式**：TC-M 系列自动化（API 模式），P0 级别。
>
> **权限矩阵模板**：为每个模块生成以下矩阵（✅=允许，❌=拒绝，⚠️=部分允许）

| 接口 | SUPER_ADMIN | TENANT_ADMIN | 普通用户 | 未认证 |
|------|-------------|--------------|---------|--------|
| GET  列表 | ✅ | ✅ | ✅/❌ | ❌(401) |
| GET  详情 | ✅ | ✅（本租户） | ✅/❌ | ❌(401) |
| POST 创建 | ✅ | ✅（本租户） | ❌(403) | ❌(401) |
| PUT  更新 | ✅ | ✅（本租户） | ❌(403) | ❌(401) |
| DELETE 删除 | ✅ | ✅（本租户） | ❌(403) | ❌(401) |

### TC-M01: {模块名} 权限矩阵验证

| 字段 | 内容 |
|------|------|
| **优先级** | P0 |
| **覆盖角色** | SUPER_ADMIN / TENANT_ADMIN / 普通用户 / 未认证 |
| **测试步骤** | 1. 准备各角色的 token<br>2. 对每个接口分别用各角色 token 调用<br>3. 断言响应符合矩阵定义 |
| **预期结果** | 每个角色的响应码与权限矩阵一致 |
| **关联需求** | 权限设计文档 |
| **设计方法** | 判定表 |

> **质量自检追加项（安全 + 幂等 + 权限矩阵）：**
> - [ ] 每个新增接口至少有 1 条 TC-S 水平越权验证（多租户接口必须）
> - [ ] 每个 POST 创建接口至少有 1 条 TC-I 幂等性验证
> - [ ] 每个核心模块有权限矩阵表，并有对应 TC-M 用例覆盖 4 个角色

## 优先级定义

| 等级 | 含义 | 发布阻断 | 对应测试执行策略 |
|------|------|----------|----------------|
| P0 | 核心流程/阻塞性缺陷 | 必须 100% 通过 | 第一阶段必须全部通过才能继续 |
| P1 | 重要功能/常用路径 | 发布前必须执行 | 第二阶段执行，失败记录 Bug |
| P2 | 次要/罕见路径 | 时间允许时执行 | 第三阶段执行，可推迟修复 |

### 测试执行分层策略（与 e2e-playwright 技能对齐）

生成测试用例时，每条用例的优先级决定其在执行阶段的处理方式：

```
阶段1 — 核心链路（P0）：先跑 P0，有失败立即停止修复
阶段2 — 完整接口（P0+P1）：P0 通过后再跑全部 API 用例
阶段3 — 端面/回归（P1+P2）：接口全绿后执行 UI 和回归
```

**P0 用例判定标准**（以下场景必须标注 P0）：
- 登录/认证核心流程
- 主实体的创建、查询（正向）
- 核心状态转换主路径（如状态机的主流程）
- 所有 RG-N 回归用例
- 权限边界（401/403 校验）

**P1 用例判定标准**：
- 编辑、删除操作
- 反向/错误场景（参数校验失败、重复创建等）
- 边界值验证
- 非核心状态转换

**P2 用例判定标准**：
- 极端边界值（超长字符串、特殊字符）
- 低频操作路径
- UI 体验审查（TC-UX）

## 测试失败归因规范（强制）

测试用例设计完成后，若执行阶段出现断言失败，必须按以下判定框架归因，**不得直接修改断言或跳过用例**。

### 归因判定优先级

```
1. requirements.md（FR-N 验收标准）→ 最高优先级
   └─ 此场景在 FR 中有明确预期 → 以 FR 为准，程序不符则是程序错误

2. design.md（API 设计/状态转换/不变行为）→ 第二优先级
   └─ 响应格式/错误码/状态流转在 design 中有定义 → 以 design 为准

3. tasks.md（Acceptance 标准）→ 第三优先级
   └─ Acceptance 中有约束 → 以 tasks 为准

4. 行业最佳实践（以上均未覆盖时使用）
   └─ REST 规范、HTTP 语义、业界 SaaS 惯例
   └─ 使用时必须在报告中注明具体依据来源
```

### 归因结论与处置

| 结论 | 触发条件 | 处置 |
|------|---------|------|
| **程序错误** | 实现与 FR/design/tasks 定义不符 | 修复程序，断言不变 |
| **脚本错误** | 断言写法有误，实际行为符合 FR/design | 修正断言，记录调整理由 |
| **文档未覆盖** | 三份文档均无定义 | 采用行业实践补充，报告注明来源 |
| **文档冲突** | 各文档定义不一致 | 停止判定，向用户提出澄清 |

### 断言调整必须在报告中记录

每次调整断言（无论原因），必须在测试报告中补充以下记录：

```markdown
### 断言调整说明（本轮）

| 用例 | 原断言 | 调整后断言 | 归因结论 | 判定依据 |
|------|--------|-----------|---------|---------|
| TC-XXX | `toBe(0)` | `toBe(200)` | 脚本错误 | design.md §3.2 响应码定义为 200 |
| TC-NXX | `toContain('已存在')` | `toContain('重复')` | 文档未覆盖，采用行业实践 | REST 错误信息应含冲突资源描述（RFC 7231 §6.5.8） |
```

**不允许无记录地修改断言**，即使是"明显笔误"也需简短说明。
